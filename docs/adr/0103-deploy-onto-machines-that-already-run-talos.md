# 0103. Deploy onto machines that already run Talos

Status: Accepted; built · Date: 2026-10-29 · Design section: Bootstrap (`ichor adopt`), Nodes, Cilium · Builds on: 0014, 0042, 0066, 0075, 0076, 0077, 0099, 0101

Amended by [ADR 0104](0104-a-cluster-with-no-cni-gets-ichors-cilium-before-ichor-and-ichor-is-installable-with-helm.md): a cluster with no CNI is adopted as managed Cilium (Ichor installs it first), not unmanaged `talosCNI: none`; the network-policy gate follows live detection; the "No CNI installed" row of 1.1 and open question 3 are superseded.

Decided: Ichor adopts a running Talos cluster on Talos v1.14 or later (older is refused with "upgrade Talos first"); a Cilium cluster is taken over as Ichor's own Helm release through a diff-checked `TakeOwnership` Job, while any other CNI (and a Cilium the user wants left alone) is adopted only on the operator's explicit request in a new CNI-unmanaged mode, `spec.cni.preset: unmanaged`, in which Ichor neither installs, operates nor renders the CNI and skips its CiliumNetworkPolicies unless Cilium is present; it recovers the cluster's secrets bundle from a control plane's machine config, holds every adopted machine until zero drift is verified, only advises (never starts) a CA rotation afterwards, and refuses to join an already-configured node unless that node is reclaimed, either by `ichor reclaim node` with the operator's own talosconfig or, as an override path that is off by default, from the UI through a short-lived, single-node, auto-deleted credential Secret, a typed-UUID confirmation and an audit Event; reclaim resets only STATE and EPHEMERAL

## Decisions by the user (2026-10-29)

These answered the questions this ADR first raised; the sections below are rewritten to match.

1. **Non-Cilium CNI on adoption**: not refused. A CNI-unmanaged mode is designed (1.1a). Fresh `ichor init` stays Cilium-only; unmanaged exists only for adoption.
2. **Reclaim**: both paths, the CLI with the operator's own credential and a UI/controller path with a short-lived Secret (section 2).
3. **CA rotation after adoption**: advice only, printed and shown, never started automatically (1.4).
4. **Minimum version**: Talos v1.12 or later; older is refused with a message to upgrade Talos first (1.9).

## Context

The user asked to think about deploying onto machines that already have Talos installed. Two situations are meant, and Ichor handles neither well today.

1. **A running cluster Ichor did not create**, brought under management (`ichor adopt`).
2. **One machine that already runs Talos, configured, added to an Ichor cluster.** Ichor's join flow starts from maintenance mode (ADR 0076); a configured node never reaches it.

Constraints from the repo: Cilium is the only CNI and Ichor's own Helm release (ADR 0099, kept by 0101); Argo CD, Kokumi and every GitOps tool are out of scope (0101); machine config is typed only, so a difference that is not a `SysctlConfig`/`KernelModuleConfig` document cannot become a patch (0014, 0075, 0077); the controller is the only writer to nodes, except that `init`, `adopt` and full-loss recovery predate the cluster and run in the CLI (architecture, "CLI and UI"); a reset names `STATE` and `EPHEMERAL` explicitly (0042).

### What `ichor adopt` did before this ADR

- It needs `--cluster`, `--secrets-bundle FILE` (a `talosctl gen secrets` file; the flag is required) and the operator's talosconfig. It dials nodes read-only.
- It **creates nothing but `TalosConfigPatch` objects**. `runAdopt` Gets the `TalosCluster`, lists `TalosMachine`s and patches, and Creates patches. The `TalosCluster`, the bundle Secret, the `TalosMachine`s, the approvals and Ichor itself must already exist. No command creates them for a cluster Ichor did not build.
- Per approved machine it reads the live config, renders a baseline, and diffs (`controller.ChangedPaths`). Only `SysctlConfig` and `KernelModuleConfig` are captured; a patch is returned only if render plus patch equals the live bytes. Everything else is reported by path with a hint (`specFieldHints`, ADR 0077). Unapproved machines are skipped (0075). A machine with JWT authenticators is refused (0094).
- It knows nothing about the CNI beyond a hint that flannel is unsupported. It does not read Kubernetes state, kube-proxy, KubePrism or inline manifests, and it never touches Cilium.
- The render drops only an inline manifest named `cni` (`pkg/cni.InlineManifestName`, `dropHandedOverInlineManifest`). An existing cluster's Cilium entry has whatever name its author chose.

## Findings

### Helm SDK v3.21.4 (`helm.sh/helm/v3`, the version in `go.mod`, read from the module cache)

- `Install` with `TakeOwnership` calls `requireAdoption` instead of `existingResourceConflict` (`pkg/action/install.go:353`, `validate.go:41`). `requireAdoption` only checks that each object exists. `checkOwnership` (the `app.kubernetes.io/managed-by: Helm` label and the two `meta.helm.sh/release-*` annotations) is skipped. So **`TakeOwnership` works on objects with no Helm metadata (Talos inline manifest, `helm template | kubectl apply`) and on objects owned by a different release name or namespace.** Without it those installs fail with "invalid ownership metadata".
- Before that, `setMetadataVisitor(..., force=true)` rewrites the ownership label and annotations on the rendered objects, so they carry Ichor's release afterwards (`install.go:339`).
- The objects are then updated with `UpdateThreeWayMerge(toBeAdopted, resources)` (`install.go:461`). In `requireAdoption` the infos appended are the *rendered* ones (the live object is read and thrown away), so "original" equals "target". Reading `createPatch` (`pkg/kube/client.go:640`) the consequence is: fields that differ are overwritten by the chart's values, but **live-only fields are kept and live-only objects are never deleted**, because nothing in the new release's manifest records them. Adoption converges the rendered fields and silently keeps the rest. This follows from reading `createPatch` in the Helm source.
- `availableName` looks for a release of that name **in the storage backend `cfg` points at** (`install.go:533`). Ichor stores records in `ichor-system` (ADR 0099, departure 2). A user's `sh.helm.release.v1.cilium.vN` in `kube-system` is therefore invisible: Install does not fail on a name clash, it creates a second, independent revision 1. Two Helm histories would then describe one set of objects, and a later `helm upgrade` by the user would fight Ichor.
- `Upgrade` also has `TakeOwnership` (`upgrade.go:121,347`), but Ichor's `Apply` only runs it after an Ichor-side record exists.
- Chart `crds/` handling (`installCRDs`) runs on Install; the pinned Cilium chart is checked for a `crds/` directory by the takeover library.

### Talos v1.14 (docs.siderolabs.com)

- Inline manifests are created and never updated or deleted by Talos; a values change needs `upgrade-k8s`. Therefore an inline-manifest Cilium cannot be left in the machine config once Ichor owns the release (ADR 0099, decision 2): the entry has to go, or a Kubernetes upgrade can re-apply it over the Helm release.
- `talosctl reset` accepts `--system-labels-to-wipe`, `--graceful` (cordon, drain, leave etcd; default true) and `--reboot`; ADR 0042 already fixed the request Ichor sends.
- `secrets.NewBundleFromConfig(clock, config.Config)` exists in machinery v1.14.3 (`config/generate/secrets/bundle.go:203`). It rebuilds the bundle (OS, Kubernetes, aggregator and etcd CAs, service-account key, cluster ID and secret, trustd token, bootstrap token, secretbox secret) from a control plane's loaded config, tolerating the v1.14 multi-document form.

## Decision

### 1. Adopting a running cluster

**1.1 The CNI decides the mode; Ichor never migrates one.** `ichor adopt` first runs a read-only inspection and prints a report. Provenance is classified from the node config and the Kubernetes API, not from names alone:

| Found | Result |
|---|---|
| Cilium, Ichor-bootstrapped | Already handled; adopt only checks the release exists. |
| Cilium from a Helm release (`helm`, `cilium install` of the Cilium CLI, which also writes a Helm release) | Take over (1.2, case B), or adopt unmanaged with `--cni-unmanaged`. |
| Cilium from a Talos inline manifest or an applied `helm template` | Take over (1.2, case C), or adopt unmanaged with `--cni-unmanaged`. |
| Talos's own flannel (`KubeFlannelCNIConfig`, `cluster.network.cni.name: flannel` or unset) | **Unmanaged only**: refused with the explanation below unless `--cni-unmanaged` is given. |
| Calico, another CNI, or `cni.name: custom` without manifest URLs | **Unmanaged only**, same. |
| `cluster.network.cni.name: custom` with `urls` (Talos applies the manifests) | Those URLs are an unrepresentable config path (class C, 1.7); the machine blocks. |
| Mixed (Cilium DaemonSet plus a second CNI's DaemonSet, or two CNI configs under `/etc/cni/net.d`) | **Refuse**, naming both, even with `--cni-unmanaged`: Ichor cannot say what it is leaving alone. |
| No CNI installed (`cluster.network.cni.name: none`, nodes NotReady) | Unmanaged with `talosCNI: none`. Installing Cilium onto it is an open item. |

The mode is never chosen for the user. Without `--cni-unmanaged`, a non-Cilium cluster is refused with nothing written (no Secret, no CR, no node call beyond reads), and the message names the CNI found and says: "Ichor will not install or operate it; to adopt the cluster with the CNI left exactly as it is, run again with --cni-unmanaged." Where the CNI is Cilium, the report offers both outcomes. The inspection is identical in both modes.

**1.1a The CNI-unmanaged mode.** The user asked whether CNI management can be turned off, so that a cluster with any CNI is adopted. It can, as an explicit mode with these properties.

*What it means.* The adopted cluster keeps whatever CNI it runs. Ichor does not install it, upgrade it, tune it or hand it over. Everything else keeps working: Talos and Kubernetes upgrades, CA rotation, config rollout, etcd backup and restore, node add/remove, reclaim, drift reporting.

*API choice.* A new enum value `unmanaged` on the existing `spec.cni.preset`, plus one new optional struct, `spec.cni.unmanaged`, with a single field `talosCNI` (`default|none`, default `default`):

- `default`: the machine config has no CNI selection (Talos runs its own flannel, or whatever `cluster.network.cni` selects by default). Render emits nothing about the CNI.
- `none`: render emits `cluster.network.cni.name: none` (the live value), because the baseline otherwise defaults to flannel.

Nothing is reused from retired values: `flannel` and `custom` stay refused (ADR 0099 decision 8) and keep meaning "removed", so a stored `preset: flannel` object is not silently reinterpreted as hands-off. The enum gains a value (append-only: the installer's additive check does not read `enum`, ADR 0099); `spec.cni.unmanaged` is a new property. `spec.cni.kubeProxy` keeps its field with a defined meaning in this mode: it records the Talos kube-proxy setting the node already has (`enabled`: Talos runs kube-proxy; `replaced`: it is disabled in Talos) so the render reproduces it, and it is no longer something Ichor switches (see below).

*Why a preset value and not `spec.cni.managed: false`.* (a) The preset is already immutable by CEL (`self.preset == oldSelf.preset`) and already the one switch every render, webhook and controller branch reads (`cniPresetFor`, `networkinstall.go`, `CNIUnsupported`); an unmanaged value is one more branch of the same switch and inherits immutability, which matters because turning management on or off changes the machine config (flannel document, kube-proxy, inline entry) of a running network. A mutable boolean would be a way to flip that by editing a field. (b) A boolean is orthogonal to the preset and so admits meaningless pairs (`preset: cilium, managed: false, cilium.values: {...}`, or `managed: false` with `tunnel` set) that each need a CEL rule and a runtime check; with a preset value the existing "only applies to the cilium preset" rules (`tunnel`, `cilium.values`) already forbid them. (c) It cannot be confused with the deprecated values: those say the cluster is unsupported; this one says it is supported and hands-off. The cost: a cluster cannot move between managed and unmanaged without being recreated, which matches ADR 0099's stance that a CNI change is not an in-place operation. Rejected: a new top-level `spec.networking.mode` (a second place describing the same thing).

*What is disabled* (each by a check, not only by hiding):

- The `ichor-cni` Job is never created: `CNIHandoverReconciler` returns early for `unmanaged`; no `CNIHandover`, `CNIValuesApplied` or `CiliumUpgradeAvailable` conditions are set, and `cniHandoverPending` is false so a Kubernetes upgrade is never blocked on a hand-over that cannot happen.
- `spec.cni.cilium` is refused by CEL for this preset, so there is no values page to write to; `ichor get|edit|apply cni-values` and `ichor upgrade cni` and their `CniService` calls return "the CNI is not managed by Ichor (spec.cni.preset: unmanaged)".
- A `TalosOperation` of kind `cni` (chart upgrade, kube-proxy switch) is refused by the webhook for an unmanaged cluster, and the executor re-checks.
- The kube-proxy switch is disabled. The operator who changes Service routing owns that change; Ichor's consistency check (ADR 0066) between Talos kube-proxy and Cilium's replacement is skipped, since there is no Cilium contract to compare with.
- Render leaves the node's CNI configuration as the live node has it: no `KubeFlannelCNIConfig` `$patch: delete` document, no `cni.name` change, no inline `cni` entry, no KubePrism requirement or injection for Cilium (KubePrism is left as the node has it). `injectKubeProxy` writes the recorded `spec.cni.kubeProxy` value and nothing else. The CNI-relevant paths of the render equal the live ones byte for byte.
- The adopt report never lists class B CNI items (Cilium inline entry, flannel removal) for an unmanaged cluster; they are not Ichor-owned.

*What still works that touches the CNI:* Ichor keeps reading (never writing) CNI facts for display: `status.cni.detected` (`cilium|flannel|calico|other|none`, plus image tag where a DaemonSet exposes it), refreshed on a slow requeue, used by the UI/CLI and by the network-policy gate below. After a CA rotation the restart order puts the CNI first for a managed cluster, and an unmanaged cluster's CNI is not restarted (ADR 0063's amendment).

*NetworkPolicies (ADR 0100).* Ichor's own policies are `CiliumNetworkPolicy` and need Cilium. They are applied only when `status.cni.detected` is `cilium` and the `CiliumNetworkPolicy` CRD exists (the installer already tests the CRD; the gate adds the detection). Otherwise the install step and the installer Job skip them and the chart renders `networkPolicy.cilium.enabled: false`; the `ichor-system` namespace is then not isolated by Ichor, and the UI and `ichor status` say so ("Ichor's network policies are not applied: the CNI is flannel"). Ichor does not write standard `NetworkPolicy` objects in this ADR (open item). Because the gate follows live detection, a hands-off Cilium cluster gets the policies, and a user who dislikes that sets `networkPolicy.cilium.enabled=false`.

*A Cilium cluster whose user wants Ichor hands-off* is allowed with the same mode: `ichor adopt --cni-unmanaged`. Nothing is taken over, no Helm record is touched, nothing is removed from the machine config (including a Cilium inline entry, which stays and becomes the user's drift problem: render cannot express it, so it is class C and blocks the machine, see 1.7; the user who wants to keep that entry should keep it in the node's own tooling). The user may later want Ichor to own it; that needs a new cluster, since the preset is immutable.

*How the UI and CLI show it.*

- Cluster header/list: a badge "CNI: unmanaged (flannel)" using `status.cni.detected`.
- The Cilium page is replaced by a card with the title and text "CNI not managed by Ichor", the detected CNI and version, and a one-line explanation ("Ichor does not install, upgrade or configure this CNI"). No values editor, no upgrade, no kube-proxy switch; those routes return a not-found page with the same text.
- The Operations "New" dialog omits `cni` for such a cluster.
- `ichor get cluster` prints `cni: unmanaged (flannel, not managed by Ichor)`; `ichor cni ...` commands exit non-zero with the message above; `ichor adopt` prints the same line in its plan and the Ichor-owned class B list omits all CNI entries.
- `ichor init` has no `--cni-unmanaged` flag and the webhook refuses `preset: unmanaged` on create unless the object carries the adoption marker the adopt write phase sets (annotation `ichor.maesh.dev/adopted: "true"`, 1.8). It is not a general way to build a cluster without a CNI.

*Why refuse migration, still.* A CNI swap takes pod networking down; the `TalosCluster` CRD already says so and makes `cni.preset` and the tunnel immutable for that reason. A migration cannot be rolled back by Ichor once the old datapath is gone (the new CNI owns the pod CIDR and node routes), cannot be verified before it is done, and needs per-workload knowledge Ichor does not have: NetworkPolicy semantics differ between CNIs, Service routing changes if kube-proxy is also switched, and the pod CIDR and IPAM mode of the old CNI constrain Cilium's (`ipam.mode` is Ichor-owned, `kubernetes`). Cilium's own documented migration is a node-by-node dual-CNI procedure with a different overlay CIDR; wrapping it would make Ichor the operator of a rolling production network outage, which is what ADR 0099's "Ichor bootstraps CNI once" avoided. The unmanaged mode removes the cost of that stance: a flannel cluster (Talos's default) is adopted and left alone. A migration ADR can still follow, and nothing here forecloses it.

**1.2 Taking over an existing Cilium** (managed mode only; none of this runs with `--cni-unmanaged`).

Preconditions, checked before anything is written:

1. **Version.** The live Cilium minor equals the embedded chart's minor, or is exactly one lower (the existing one-minor-at-a-time rule for `cni` operations, architecture "Upgrades"). Otherwise refuse and say to upgrade with the tool that installed it first. Adoption of an older minor is an upgrade; it is announced as one.
2. **Ichor-owned keys.** The live configuration is compared with the keys Ichor owns (ADR 0099, decision 3): `ipam.mode` (must be `kubernetes`; a `cluster-pool` Cilium is **refused**, changing IPAM renumbers pods), `kubeProxyReplacement` (maps to `spec.cni.kubeProxy`, 1.5), `tunnelProtocol` (maps to `spec.cni.tunnel`; immutable afterwards), `k8sServiceHost`/`k8sServicePort`, the Talos capability and cgroup keys. A value that Ichor would change on a running data plane (other than the capability and cgroup keys, which Ichor makes match the Talos guide) is reported and requires `--accept-cilium-changes`; IPAM and tunnel protocol are never accepted.
3. **Values.** Case B: the user values are decoded from the newest release record (`sh.helm.release.v1.cilium.vN`, base64, gzip, JSON, field `config`) and become `spec.cni.cilium.values` after removing owned keys, which are then checked as in step 2. Case C has no record, so the operator supplies `--cilium-values FILE` (what they gave `helm template`); without it adopt uses the Ichor defaults and the diff in step 4 will show what is missing.
4. **Diff gate.** Ichor renders the pinned chart with the effective values (the same `EffectiveValuesFor` path as bootstrap) and compares every rendered object with the live one, with the volatile fields removed. An empty difference proceeds. A non-empty one is printed per object and path and needs `--accept-cilium-diff`. This is the Cilium counterpart of adopt's zero-drift rule. It is needed because of the live-only-fields finding above: `TakeOwnership` would otherwise leave an unreviewed mix of chart and user state that Ichor's later `Upgrade` (`ResetValues`) interprets differently.
5. **Health.** The DaemonSet and operator are Ready on all nodes, and KubePrism answers on every node (1.6), because the Job reaches the API through `localhost:7445` while agents restart.

The takeover itself:

- It reuses the `ichor-cni` Job and `cilium.Apply` (ADR 0099). With no Ichor record, `Apply` runs `action.Install` with `TakeOwnership: true`, which is correct for both cases: B (objects carry another release's metadata, possibly another name or namespace) and C (no Helm metadata). Only the diff gate and the foreign-record handling are new. `ichor adopt --tunnel` applies only when adopt installs Cilium itself (a cluster with no CNI) and is refused on a takeover, which keeps the live tunnel.
- **Foreign release record.** After the Ichor record is written and the rollout is Ready, a foreign `cilium` record in `kube-system` (or elsewhere) is copied into a Secret `ichor-cilium-prior-release` in `ichor-system`, then deleted (the record Secrets only; never `helm uninstall`, which would delete the CNI). Deleting it is announced in the plan and part of the consent: the record Secrets are deleted only when the operator consented, each only after the backup in `ichor-cilium-prior-release` has been read back and found byte-identical, and only if it is still the Helm `cilium` record with the same UID. Leaving it would give two histories for one object set (see the `availableName` finding). Rejected alternative: point Ichor's storage at the foreign record's namespace and `Upgrade`; it keeps the user's history but breaks ADR 0099's namespaced-Role decision and the hand-over reader.
- **Inline entry.** In case C and in any cluster whose Cilium also sits in `cluster.inlineManifests`, the entry is found by content (a manifest that contains the `cilium` DaemonSet in `kube-system`), not by name, because `dropHandedOverInlineManifest` matches only the name `cni`. Its name is recorded (additive status field on the TalosCluster) so the render drops it. **Ordering:** the entry is removed from the machine config only after the Helm record is `deployed` and the DaemonSet Ready (`CNIHandover`, unchanged in shape). If takeover fails nothing on the nodes has changed. Other inline or external manifests are not touched and make the machine's drift unrepresentable (1.7).
  *Wiring:* `ichor adopt` finds the entry with `cilium.FindInlineManifest` and writes its name in the annotation `ichor.maesh.dev/cni-inline-manifest` at create time; the CNI hand-over controller copies it to `status.cni.takenOverInlineManifest` in the same status update that sets `CNIHandover=True`, and render reads only the status. The `ichor-cni` Job gets `--takeover` for every Job of an adopted cluster until the hand-over completes (a retry after a failed first run still retires the foreign record; the retirement is idempotent), and it needs get/list/delete on Secrets in kube-system only (Role `ichor-cni-records-role`). `cilium.Preflight` runs the preconditions read-only for the adopt plan.
- **The Job's rights.** The `ichor-cni` Job's ServiceAccount holds, in kube-system only, the Secret rights of the chart's `hubble-generate-certs` Role, rule for rule from the embedded chart: `create` on Secrets (not name-scoped), `update` on the five hubble secrets, and `get` and `update` on `cilium-ca`. It has no `escalate` verb for that. The Role and its binding are in the chart and the install manifest, and the installer's `bind` and `escalate` list names it (ADR 0108). Helm's escalation check refuses to create a Role that grants a rule its caller does not hold, and a `create` on Secrets cannot be name-scoped, so the mirror is required for the create.
- No rollback of an adoption (Atomic would uninstall a running CNI, ADR 0099). A failed Install leaves a `failed` record; the next run goes to `Upgrade` (as `Apply` already does). A rerun that finds Ichor's own `cilium` record left `pending-install` by an interrupted install repairs it before installing again, because Helm refuses every later operation on a pending record ("another operation (install/upgrade/rollback) is in progress"). Whoever holds the CNI lock (the adopt run, or the `ichor-cni` Job, which runs exclusively) repairs a pending record at once instead of waiting out the 10-minute apply timeout, and the controller retries a failed `ichor-cni` Job after a back-off of about a minute instead of leaving `CNIHandover=False` for good.

**1.3 The cluster's secrets bundle.** `ichor adopt` takes either `--secrets-bundle FILE`, used as given, or `--recover-secrets` with `--recover-from ADDRESS`, and not both. `--recover-secrets` reads one control plane's machine config over the Talos API with the operator's talosconfig and builds the bundle with `secrets.NewBundleFromConfig`, then `Validate`s it against the chosen version contract. Recovery is read-only on the node. The result is written under `~/.ichor/clusters/<name>/` with mode 0600, as `init` does, and the operator is told to back it up; nothing is printed. A wrong or partial bundle cannot get through: the render uses it, so any secret field that differs from the live config appears in the zero-drift diff (1.7) and no patch is produced. The three-CA PKI (Talos, Kubernetes, etcd) is unchanged; Ichor does not rotate anything during adoption.

**1.4 The talosconfig.** It is the operator's own and is used only by the CLI, read-only, never stored, never sent to the controller (as ADR 0014 decided). `--talosconfig` gains `--context` (the file may hold several clusters). The node list comes from the control plane's discovery membership, not from typing every address. After adoption the controller uses a certificate minted from the recovered bundle (its short-lived `os:admin` identity, architecture "Trust"). The operator's old client certificate stays valid until it expires or a CA rotation (ADR 0063, 0091). **CA rotation is advice only.** When adoption finishes, `ichor adopt` prints a recommendation ("the Talos and Kubernetes client certificates of the previous administrators, and the CA keys held by whoever created this cluster, remain valid; consider `ichor rotate ca`"), the UI shows the same text as a dismissible notice on the cluster page, and the cluster carries a condition `CARotationAdvised` (True, reason `Adopted`, cleared by the first completed rotation or by dismissal, which is an annotation written by the user). Nothing starts a rotation: no flag chains it to adopt, no controller creates the `TalosOperation`. The recommendation is the same in unmanaged-CNI mode.

**1.5 kube-proxy mode detection.** In unmanaged mode only the Talos side is read, and the result is written to `spec.cni.kubeProxy` as the recorded setting (`enabled` when Talos runs kube-proxy, `replaced` when disabled); there is no consistency check. In managed (Cilium) mode both sides are read and must agree:

- Talos side: `KubeProxyConfig.enabled` (v1.14) or `cluster.proxy.disabled` (legacy), plus whether the `kube-proxy` DaemonSet exists.
- Cilium side: the `kube-proxy-replacement` key of the `cilium-config` ConfigMap.

Mapping to `spec.cni.kubeProxy`: Talos proxy enabled and replacement off gives `enabled`; Talos proxy disabled and replacement on gives `replaced`. Disabled with replacement off (no Service routing) and enabled with replacement on (works, two owners) are **refused** with the reason, because Ichor's consistency check (ADR 0066) would mark the cluster unhealthy from its first minute and the fix is a switch the operator should make deliberately. The CRD default is `enabled`, so adopt always writes the detected value; it never relies on the default.

**1.6 KubePrism** (a precondition of every adoption that ends in an Ichor-managed Cilium, whether a takeover or a bootstrap on a cluster with no CNI; an unmanaged adoption leaves it as the node has it). Ichor's Cilium Job and its replaced-mode values reach the API through KubePrism on `localhost:7445` on every node (ADR 0099). It is detected from `machine.features.kubePrism` or the `KubePrismConfig` document. When it is off, or on another port, on any machine, adopt refuses up front with nothing written, in `enabled` as well as `replaced` kube-proxy mode: enabling KubePrism needs a reboot that adopt's hold release never orders, so an Ichor-owned change that enables it would deadlock (the Job could not reach the API, and the holds are released only after the Job).

**1.7 Machine config drift on adoption.** The single "zero drift or nothing" rule of ADR 0014 stays for what patches can express. Three classes replace the two (patch, unrepresentable):

- **A. Representable**: sysctl and kernel-module documents, and values that now have spec fields (subnets, install disk, ADR 0077). Captured or mapped as today.
- **B. Ichor-owned** (managed mode only; empty of CNI items when unmanaged): the Cilium inline entry (1.2), kube-proxy (when `replaced`), flannel removal. The render will change these on its first apply. They are listed, need the plan's consent, and do not block.
- **C. Unrepresentable**: everything else in the legacy `Config` document and any other inline or extra manifest. Blocks that machine, as today, with the path list and hint.

Two additions make this workable:

- **Version contract probing.** The `TalosCluster.spec.versionContract` is chosen by rendering at each contract from the nodes' running version downwards, never below v1.12 (1.9), and taking the one with the fewest class C paths, not assumed equal to the running Talos version. A cluster generated on an old `talosctl` and upgraded in place has a legacy-form config; forcing v1.14 turns every field into drift (the ADR 0075 failure). The result is shown and can be overridden.
- **Hold.** The controller applies drift on every approved machine as soon as it exists. So `adopt` creates each `TalosMachine` with the annotation `ichor.maesh.dev/hold-apply: "true"`, which the machine reconciler reads: it computes and reports drift and never applies. Adopt removes the annotation, machine by machine, only after the live zero-drift check passes and the operator confirmed class B. No CRD field is added.

**1.7a Class A on a fresh adopt: install, registry mirrors and certificate SANs.** A `talosctl`-made cluster states an installer image and disk, usually a registry mirror and extra certificate SANs. `ichor adopt` maps them instead of blocking every machine as class C, and on a fresh adopt it writes them itself, so a rerun's plan has zero drift.

- **Install.** `UnattendedInstallConfig` (v1.14) and `machine.install` (v1.12 and v1.13) map to `TalosMachine.spec.install`: `disk` from `installDisk` or from a disk selector that is exactly one of the five equalities Ichor renders (wwid, serial, by-id symlink, bus path, device path; any other selector, such as a size range, has no field and stays class C), `image`, and `wipe`. `wipe` is a new additive field, default false. A live `wipe: true` is recorded, not ignored: the install-time-only classification would otherwise leave that machine's drift unapplied for ever, and Talos reads the flag only at install, so on a running node it does nothing. Extra kernel arguments, extensions and the bootloader options still have no field.
- **Registry mirrors.** `RegistryMirrorConfig` documents and `machine.registries.mirrors` map to `TalosCluster.spec.registries` (host, endpoints), with two new additive fields, `skipFallback` and `overridePath` (one flag for all of a host's endpoints; a host with mixed per-endpoint values is not mapped). Every node must state the same mirrors, else nothing is mapped and the difference is class C. Render emits the mirrors as `RegistryMirrorConfig` documents from contract v1.12, the form Talos's own generator uses there (below v1.12 it keeps `machine.registries.mirrors`); credentials stay in the legacy `machine.registries.config`, which Talos folds with the documents host by host. That changes the rendered bytes of an existing v1.12+ cluster that has `spec.registries`; both forms are hot-applied (fieldmeta classes them safe). The drift comparison (`controller.ChangedPaths`, used by the reconciler and by adopt alike) normalises both forms into one representation on both sides before diffing, so the same mirrors in either form are not drift, and a node whose mirrors are in the legacy form (generated before v1.12, upgraded in place, or configured by an earlier Ichor build) is not class C and stays Ready; different endpoints, `skipFallback` or `overridePath` still are drift. The node moves to the document form only when it is applied for another reason. **Credentials and TLS are never mapped**: `RegistryAuthConfig`, `RegistryTLSConfig` and `machine.registries.config` stay class C, with the hint to create the TalosCluster first with `spec.registries[].authSecretRef`, so no password reaches a spec or a plan line.
- **Certificate SANs.** No spec field existed, and a TalosConfigPatch cannot carry them: `KubeAPIServerConfig` is not a patch document kind, and a `Config` patch must restate the secret `machine.token`. So `TalosCluster.spec.certSANs` is a new additive field, handed to the generator's `WithAdditionalSubjectAltNames`, which writes `machine.certSANs` and the kube-apiserver SANs (`KubeAPIServerConfig.certExtraSANs`, `cluster.apiServer.certSANs` below v1.14) from one list, as `talosctl gen config --additional-sans` does. It is mapped only when every node states the same `machine.certSANs` and every control plane the same kube-apiserver SANs; otherwise the paths stay class C. The render adds no SAN of its own (the endpoint host is not added).
- **Hints.** Class C paths that share a hint are printed on one line, and the hints name `spec.install`, `spec.registries` and `spec.certSANs`.

**1.8 Order and what is written.** `ichor adopt` becomes four phases; each ends at a state in which nothing has been applied to a node.

1. `--plan`: prints the inspection and the plan and writes nothing anywhere. Without it adopt shows the same plan and asks for consent, which `--yes` skips.
2. Write: the bundle Secret, the `TalosCluster` (contract, subnets, `cni.preset: cilium` or `unmanaged` with `unmanaged.talosCNI`, `kubeProxy`, annotation `ichor.maesh.dev/adopted: "true"`), `TalosMachine`s (identity read over the authenticated API, role, install, held), `TalosConfigPatch`es, Ichor's install manifest if Ichor is not yet running (the same step `init` does; the network-policy gate of 1.1a decides whether the Cilium policies are included). All held. `--node ADDRESS` seeds discovery of a cluster that has no `TalosCluster` yet, and `--version-contract` overrides the probed contract.
3. Cilium takeover (1.2); skipped in unmanaged mode.
4. Release the hold per machine: first render is applied by the controller, control planes one at a time under the cluster lock like any config rollout (ADR 0080). Release is one machine at a time, control planes first, each waiting for Ready without `AdoptionHeld` before the next. A held machine reports the condition `AdoptionHeld`.

`ichor init` and `ichor adopt` write approved machines at addresses outside `spec.discovery`, so the user needs `update` on `talosmachines/endpoint` as well as `approve` on `talosmachines/approval` (ADR 0108; `ichor-admin` has both). Add by IP and reclaim put the address in `spec.discovery.addresses` first, so the endpoint is declared.

**1.9 Minimum version: Talos v1.12.** `ichor adopt` reads the Talos version of every node it will adopt (and the Kubernetes version) before anything else, and refuses a cluster with any node below v1.12.0 with nothing written and the message "Talos X.Y.Z is older than the oldest version Ichor adopts (v1.12). Upgrade Talos first, with talosctl or your usual tool, and run adopt again." A mixed cluster (some nodes at or above v1.12, some below) is refused the same way, naming the nodes. Contract probing (1.7) stops at v1.12, so the render path to be supported is v1.12 (legacy `Config` form), v1.13 and v1.14 (multi-document). The Kubernetes minimum is whatever Talos v1.12 supports and the pinned machinery validates; adopt does not add a second number.

**1.10 What other operations check after an adoption.**

- The removed-API check of a Kubernetes upgrade (`RemovedAPIsInUse`) dials a control plane, never the node under upgrade: it asks every control plane for the admin kubeconfig and reports the union of what they find, because a worker's Talos API refuses the admin kubeconfig ("kubeconfig is only available on control plane nodes"). A control plane that cannot answer makes the check Unknown.
- The Cilium compatibility rule of an upgrade (ADR 0115) is applied only when the observed CNI is Cilium. A flannel cluster adopted unmanaged is not judged by flannel's version read as a Cilium version (`cilium 0.28.9 is not known`).
- The CNI detection (`status.cni.detected` and its version) refreshes every ten minutes and also when `CNIHandover` turns True or a `cni` operation completes (`cniDetectTrigger`), so an upgrade gate does not judge a stale Cilium version right after a takeover.

**1.11 `ichor init` and `ichor adopt` write only after the controller can serve its webhooks.** The install manifest, with its validating webhook configuration, is applied before the controller pod exists, and the Service `ichor-webhook-service` has no ready endpoint until the controller is Ready, so the API server refuses every Ichor write with `connection refused` for the controller's start-up (image pull, container start, first readiness probe). It is not a policy: no CiliumNetworkPolicy exists in `ichor-system` yet, because the four policies are applied after the controller is Ready (ADR 0100). Retrying the write covered the window, but printed one refusal per attempt and bounded the wait at 30 minutes (`init`) and 15 (`adopt`), so it is replaced.

`createWhenWebhooksUp` (every CR write of `init` and `adopt`, and `createIchorInstallation`) first waits until the controller can serve the webhook, then writes. Ready means both:

- the Deployment `ichor-controller-manager` in `ichor-system` is rolled out (its generation observed, all replicas updated, no old replica left) with at least one available replica;
- the Service `ichor-webhook-service` has an EndpointSlice endpoint that is ready (a missing `ready` condition counts as ready, per the API).

The wait polls on the existing pod diagnostics (`waitDiag`), so a cluster with no pod network still fails early. After it, the write goes through `createRetrying`, which also retries a webhook refusal (an InternalError naming a webhook) but only inside `initRetryWindow` (3 minutes): that covers the short gap between a ready endpoint and the API server picking up the webhook's CA bundle. There is no second long loop.

The bound is unchanged: 30 minutes for `init` (a first install pulls images over a slow link, and a fresh install must not fail on a shorter default; ADR 0104) and 15 for `adopt`. `--wait-timeout` sets it; `adopt` had the flag and `init` gets it. A timeout fails with: `the controller Deployment ichor-controller-manager in ichor-system is not Ready after 30m0s (<pod reasons>): <what is missing>; check "kubectl -n ichor-system get pods"`. The names are the manifest's and the chart's defaults (release `ichor`, namespace `ichor-system`): a Helm release with another name or namespace is not found by label and the wait times out with that message, and an operator who may not read EndpointSlices is judged on the Deployment alone.

### 2. Adding a machine that already runs Talos

Four states must be told apart: (i) maintenance (existing flow, ADR 0076); (ii) configured by a foreign cluster; (iii) configured by this Ichor cluster (a returning machine; recognised by identity and cluster ID, handled by the authenticated path); (iv) installed but STATE wiped, which is maintenance.

For (ii), discovery cannot read identity (a configured node's API requires a client certificate), so today it fails with a TLS error and, per ADR 0011, registers nothing. Discovery now reports **`AlreadyConfigured`** as an Event and in the add-by-IP response when it sees a Talos API that completes a TLS handshake but rejects an insecure call. Nothing is created.

**Decision: refuse by default; reclaim only on an explicit request, by one of two paths that share one implementation.** Path 1 is the CLI with the operator's own credential (2.1). Path 2 is a UI/controller path fed by a short-lived Secret (2.2), an override feature that is off by default. Both run the same checks, build the same reset request and require the same typed UUID.

#### 2.1 CLI path

```sh
ichor reclaim node ADDRESS --talosconfig FILE [--context C] [--confirm UUID]
```

- It is an in-process Talos write by the CLI, the same kind of exception as `init` and `adopt` (the node is not yet part of any Ichor cluster, and the credential is a foreign admin certificate that never leaves the operator's machine).
- Steps: authenticated read of identity, hostname, role, the foreign cluster's name and ID, disks, user volumes and, for a control plane, etcd members and health. It prints this, then:
  - **Refuses** if the node's identity or cluster ID is already an Ichor `TalosMachine` or cluster (state iii).
  - **Refuses** a control plane whose removal would break its cluster's etcd quorum, or the last control plane of a reachable cluster, unless `--force` and a second typed confirmation.
  - Uses `Graceful: true` (cordon, drain, leave etcd) when the foreign cluster is healthy and reachable from the node (the Kubernetes Node object of a graceful reset stays in the old cluster, NotReady and cordoned); `Graceful: false` only with `--force-ungraceful` when it is dead.
  - Sends exactly the request of ADR 0042 (`STATE` and `EPHEMERAL`, `Reboot: true`), built by the same code, so one place defines what a reset wipes. User disks and non-system volumes are not touched, but they are listed as orphaned, and encrypted ones are called out: after such a reset the data on an encrypted disk may be unreadable.
  - Requires **typed consent**: the operator types the node's UUID (or passes `--confirm UUID`; `--yes` does not satisfy it). Consent is the credential plus the typed identity, shown beside the cluster name that will lose the node.
  - Waits for the node to answer the maintenance API with the same UUID, then registers it through the normal add-by-IP path as a pending `TalosMachine`. A changed DHCP address after the reboot is reported with the scan hint instead of guessed.
- Without the node's credential there is no API route; the documented out-of-band routes are reinstall from the ISO or a wipe by kernel argument. The kernel-argument wipe (`talos.experimental.wipe=system:EPHEMERAL,STATE`) is a real credential-less route but not a console edit: the argument is baked into a boot asset (an Image Factory schematic with `extraKernelArgs`), the node boots that ISO once, and the machine must then be started from its disk, because the argument is acted on at every boot (it loops while the wipe ISO stays first, and a plain ISO halts with `halt_if_installed` while Talos is installed). It removes STATE and EPHEMERAL, and the node returns to maintenance with the same UUID. Ichor does not offer it; the guide names it as an out-of-band route.
- Flags: `--talosconfig`, `--context`, `--confirm UUID`, `--force` with `--confirm-cluster NAME` as the second typed confirmation, `--force-ungraceful`, `--cluster NAME` (adds the address to that cluster's `spec.discovery.addresses`, so the pending machine appears), and `--wait` (default 10 minutes). The etcd health check judges the dialled member by its own etcd status and the others by whether their peer port answers.

#### 2.2 UI/controller path (override, off by default)

The user wants reclaim available without a shell. It is the one place the controller writes to a node of a cluster that is not Ichor's, using a credential that is not Ichor's, so the design is built around that credential never living longer, going wider or showing up in more places than one reset needs. The shared code is a new package `pkg/reclaim` (inspection, the refusals of 2.1, the request builder of ADR 0042); the CLI and the controller both call it.

**Objects.** One new namespaced kind, `MachineReclaim` (append-only: a new CRD, nothing existing changes), in `ichor-system`:

- `spec.address` (one IP or host:port), `spec.credentialSecretRef` (name only, same namespace), `spec.confirmUUID` (empty until the user types it), `spec.force` and `spec.forceUngraceful` (as 2.1), `spec.ttl` (default 15 minutes, hard maximum 60).
- `status.phase` (`Inspecting`, `AwaitingConfirmation`, `Resetting`, `WaitingForMaintenance`, `Done`, `Failed`, `Expired`), `status.inspection` (UUID, hostname, role, foreign cluster name and ID, disks, volumes and which are encrypted, etcd members, the refusals that apply), `status.expiresAt`, `status.result` (the new maintenance address, or the scan hint).
- The controller never writes `spec`; the typed UUID is written by the UI on behalf of the user, as every other change is.

**Flow.**

1. The user opens Machines, "Reclaim a configured machine" (the page `AlreadyConfigured` links here), enters the address and pastes or uploads the foreign talosconfig. The UI API creates the Secret and then the `MachineReclaim` as the caller.
2. The controller reads the Secret, dials **only** `spec.address` (endpoints and nodes in the talosconfig are ignored, so a multi-node config cannot widen the scope; a talosconfig with several contexts needs the one to use named in the request), runs the read-only inspection and the 2.1 refusals (a node that is already an Ichor machine or cluster, an etcd quorum that would break, the last control plane of a reachable cluster), and stops at `AwaitingConfirmation`. Nothing has been written to the node.
3. The UI shows the inspection with the foreign cluster's name, the orphaned and encrypted volumes, and the typed-UUID box. Confirmation is the user typing the node's UUID exactly (pasting is allowed; the dialog does not pre-fill it, and `Enter` does not submit an empty or mismatching box). The UI writes `spec.confirmUUID`. The webhook rejects a `confirmUUID` that differs from `status.inspection.uuid`.
4. Only when `spec.confirmUUID` equals the freshly re-read UUID, the TTL has not passed and the phase is `AwaitingConfirmation`, the controller sends the ADR 0042 request (`STATE`, `EPHEMERAL`, `Reboot: true`, `Graceful` per the inspection). It waits for the maintenance API to answer with the same UUID and then registers the machine as a pending `TalosMachine` through the add-by-IP path, as in 2.1.
5. The Secret is deleted when the phase becomes `Done`, `Failed` or `Expired`, whichever comes first, and in any case when the TTL passes; the `MachineReclaim` itself is kept for 7 days (no credential in it) as the record and then removed by the controller.

**The credential Secret.**

- Created by the UI API in `ichor-system`, type `ichor.maesh.dev/foreign-talosconfig`, with an owner reference to the `MachineReclaim` (so deleting the CR deletes it), the labels `ichor.maesh.dev/reclaim` and the expiry in an annotation. Its only key is `talosconfig`.
- **Scoped to one node.** It is bound to `spec.address` by the controller as described above, usable once (the controller records the use in status and refuses a second reset from the same request), and never reused for another request: a new request needs a new paste.
- **Short-lived and deleted.** Deleted after use (point 5) or at `expiresAt`. A sweeper in the controller, independent of the reconcile of any one CR, deletes every Secret of that type older than the maximum TTL, so a lost CR cannot leave a credential behind. The Secret lifetime is a requeue, not a side effect of a user returning to the page.
- **Never logged or echoed.** The credential lives in a type with redacting `String`, `GoString` and `MarshalJSON` (the Talos client config is parsed into it and nothing prints the parsed struct); it is not in `status`, in Events, in error text (wrapped Talos errors are passed through a filter that keeps the address and code, not the transport detail), in the audit Event, in gRPC/HTTP access logs (the UI API's logging interceptor drops the request body for the reclaim calls by method name) or in metrics labels.
- The Secret is subject to the cluster's encryption at rest like any Secret; the UI warns that the pasted credential is stored in the cluster for up to the TTL, and that nothing prevents an `ichor-system` reader from seeing it in that window (hence the RBAC below).

**RBAC and override.**

- (Amended by ADR 0107: there is no installation switch; RBAC alone decides, and `ichor-admin` holds the verb. The UI calls it "Reset and add".) The feature is off unless the installation enables it (`IchorInstallation` Helm value `reclaim.enabled`, default `false`; the controller and the UI API refuse the calls and the Secret create when off). The controller's own permission is the namespaced `get;list;delete` on Secrets in `ichor-system` it already has for other purposes; the sweeper selects by the `ichor.maesh.dev/reclaim` label.
- A new ClusterRole `ichor-machine-reclaimer` grants `create`, `get`, `list` and `update` on `machinereclaims` (the UI API reads and confirms as the user) and the custom verb `reclaim` on `machinereclaims`; the webhook performs a `SubjectAccessReview` for that verb on every create and on every `confirmUUID` update. It is not part of any default role in the chart, including the admin role: it is bound only by an explicit RoleBinding, which is the override step. Reading Secrets of the credential type is not granted to anyone by the chart (the UI API creates them with a service identity limited to `create` of that type; it cannot read them back).
- The UI shows a banner on the dialog ("Override: this resets a machine that belongs to another cluster") and does not offer the page to a user without the verb, checked by the same SAR.
- Implementation notes. Registration is not the controller's: it never writes `spec`, so `spec.clusterRef` (optional, additive) names the target cluster and the UI API adds the address to that cluster's `spec.discovery.addresses` as the user when it creates the request; the controller waits for maintenance mode and reports `status.result` (and whether the cluster already discovers the address). `status.audit.requestedBy`/`confirmedBy` are copied from the annotations `ichor.maesh.dev/reclaim-requested-by` and `-confirmed-by`, which the writer sets and the validating webhook insists equal the authenticated user (a validating webhook cannot stamp them itself). The UI API creates the request first and the Secret after (owner reference at creation); the controller requeues until the Secret exists and expires the request at its TTL if it never does. Because ichor-ui therefore holds `create` on Secrets in `ichor-system`, a ValidatingAdmissionPolicy (`ichor-ui-reclaim-credential`) limits what that ServiceAccount may create to the credential type, the `ichor.maesh.dev/reclaim` label and the single key `talosconfig`. A finished request is kept for 7 days after its `status.expiresAt`. The etcd health check judges the dialled member by its own etcd status and the other members by whether their peer port answers; `ichor init` has no switch for `reclaim.enabled` yet (the chart has). `CreateReclaim` checks get and update on the target cluster before writing anything, and the dialog registers with the cluster only when `CanReclaim` says the caller may. `MachineReclaim.spec.address` may not be loopback, link-local, unspecified or multicast (ADR 0108).
- GitOps is not part of Ichor (ADR 0101), so no rule about tracked objects is needed.

**Audit.** The controller emits an Event on the `MachineReclaim` and on the `IchorInstallation` (so it survives the CR's removal in the namespace-level view) for: `ReclaimRequested` (user, address), `ReclaimInspected` (UUID, foreign cluster name and ID), `ReclaimConfirmed` (user who wrote `confirmUUID`, UUID), `ReclaimReset` (request sent, graceful or not), `ReclaimCompleted`, `ReclaimFailed` and `ReclaimExpired`, and `CredentialDeleted` (Secret name only). The identity is the caller recorded by the UI API (Kubernetes user name from the authenticated request) and kept in `status.audit`, not only in an Event that the cluster discards in an hour. Events never carry contents of the Secret; the same events exist for the CLI path as printed lines, since the CLI has no cluster object to attach them to.

*Why this is acceptable against "the controller never holds a credential for another cluster's nodes".* The statement protected a standing credential. This is a scoped, user-supplied, expiring one with a human typing the node's identity; the architecture's "Trust" section gets an exception paragraph, and the credential is the one thing in Ichor that is deleted by time rather than by an object's lifecycle.

Rejected: *joining without a reset.* Applying a new config with new secrets to a node that has the old cluster's etcd data and state does not give a clean member and the outcome differs by role; Ichor would also have to hold the old admin credential in the cluster. Rejected: *automatic reset by the controller* on approval; ADR 0042 made reset opt-in per object because it is irreversible, and a foreign node's data is the one thing Ichor has no record of. Both reclaim paths need the typed UUID; the UI path does not weaken that for convenience. Rejected: *storing the foreign talosconfig for reuse* (a "saved clusters" list): a standing foreign credential.

## Risks

- **Data-plane disturbance on takeover.** The pod template changes (checksums, image, args) and agents restart on every node; eBPF programs persist but a version jump or changed values can drop connections. Mitigated by the minor rule and the diff gate; how much traffic a takeover drops is a known limit.
- **Wrong diff semantics.** The live-only-fields conclusion comes from reading `createPatch`. If a later Helm version changes it, the diff gate still protects, but the gate itself needs live-object normalisation that can miss defaulted fields (false positives are safe, false negatives are not).
- **Helm half-states.** A killed Job can leave `pending-install` or a failed record; Upgrade then refuses ("another operation is in progress"). Ichor repairs a pending record itself (1.2).
- **Config applied too early.** If the hold is missing the controller would apply a render that differs from the live config. The reconciler never applies a held machine.
- **Contract probing picks a wrong contract** and hides drift as class C. It is shown, overridable, and class C blocks.
- **Reclaim wipes the wrong node or a live quorum.** Mitigated by typed UUID, cluster name on screen, the etcd checks and the Ichor-cluster refusal; the residual risk is a stale or copied talosconfig pointing at a different node than the operator believes, which the identity print is there to catch.
- **Deleting the foreign release record** removes a user's `helm rollback` path. Backed up to `ichor-system`; part of the consent.
- **Recovered bundle is incomplete** (for example, an etcd-encryption config in a non-standard shape: machinery states it extracts "our best" of the secretbox key). Caught by the zero-drift diff.
- **Version floor v1.12**: a patch release below the floor in a mixed cluster is refused, which can surprise an operator mid-upgrade (the message says so).
- **Unmanaged mode hides a broken network.** Ichor does not manage the CNI and cannot fix it; it reports node readiness and `status.cni.detected` only. The UI says what Ichor does not do so that a CNI incident is not blamed on Ichor, and not the reverse.
- **Unmanaged render drifts from the node.** If the render emitted a CNI or kube-proxy setting the node does not have, the first apply would change a running network. Mitigated by the render equaling the live CNI paths, the hold, and class C for anything the typed fields cannot express (for example a Cilium or other inline manifest, or `cni.name: custom` with URLs).
- **The Cilium Job does not hold the rules of the other kube-system Cilium Roles** (`cilium-config-agent`, `cilium-operator-ztunnel`, the `cilium` and `cilium-operator` Roles) or the `cilium` ClusterRole. A takeover does not create or change those objects when they already exist, so it is not affected; a fresh install, or a chart bump that changes them, would be. ADR 0108 records the name-restricted `bind` and `escalate` grants that cover them.
- **Override credential exposure.** The foreign talosconfig sits in a Secret for up to the TTL. Mitigated by off-by-default, the explicit verb, scoping to one address, single use, TTL and sweeper, no logging, and encryption at rest being the cluster's; residual risk is a cluster-admin reading the Secret in that window, which is true of every Secret.
- **Reclaim UI path used on the wrong machine.** Same residual risk as the CLI (a stale talosconfig); the inspection shown before the typed UUID is the control, and the foreign cluster name sits next to the box.

## Open questions, and where they stand

Answered on 2026-10-29: non-Cilium CNI (unmanaged mode), reclaim (both paths), CA rotation (advise only), minimum version (Talos v1.12). Settled since:

1. The foreign Helm release record is deleted after takeover, with a backup to `ichor-system`, as part of the consent (1.2). It applies to managed Cilium only.
2. Non-Cilium inline or external manifests in a node's config stay class C and block the machine; no patch kind for `KubeInlineManifestConfig` is added.
3. A cluster with no CNI is no longer adopted unmanaged (the amendment of ADR 0104 below).
4. `ichor adopt` installs Ichor into the foreign cluster itself, as `init` does.
5. Ichor writes no standard `NetworkPolicy` objects for `ichor-system` when the CNI enforces them but is not Cilium; it skips policies there.
6. The reclaim numbers are as designed: default TTL 15 minutes, maximum 60, 7-day retention of the `MachineReclaim` record.

## Consequences

- `adopt` stops being a patch-only step and becomes the four-phase adoption of 1.8; its read-only default plan is the first thing a user sees.
- Flannel and other-CNI clusters are adopted in the unmanaged mode; Ichor still does not migrate a CNI, and fresh `ichor init` stays Cilium-only.
- The CRD gains additive API only, and no field is removed: the `unmanaged` enum value and `spec.cni.unmanaged` on `TalosCluster`, `status.cni.detected` and the recorded inline-manifest name, and a new kind `MachineReclaim`. The hold is an annotation. `flannel` and `custom` stay refused.
- Ichor's Cilium network policies become conditional on a detected Cilium (ADR 0100 gains a gate), and a cluster without Cilium has no Ichor network isolation.
- The controller gains an override, off-by-default path that uses a user-supplied foreign credential for one reset; the architecture's "Trust" text records the exception.
- Adoption needs Talos v1.12 or later.
- `TalosClient` grows an authenticated `Identity` read; the reset request moves to a shared builder.
- ADR 0014's statement that adopt "never writes to a node" still holds: reclaim is a different command, and phase 4 is the controller's.

## Amendment (2026-10-29): ADR 0104

A cluster with no CNI is no longer adopted as unmanaged `talosCNI: none`: ADR 0104 has adopt install Cilium first and adopt it managed (the "No CNI installed" row of 1.1 and open question 3 are superseded), fixes the network-policy wiring (the policies of a hands-off Cilium cluster were skipped although live detection says to apply them), and adds the Helm install path.

## Amendment: ADR 0128 (2026-11-04)

[ADR 0128](0128-adopting-installed-talos-machines-and-clusters.md) maps this ADR against the cases a user has and closes four gaps: a machine that already carries an Ichor cluster's CAs but has no `TalosMachine` is registered with `ichor adopt --add-machine` (section 2, state iii, was not reachable before); reclaim no longer counts a stale pending `TalosMachine` as an Ichor machine and points a managed cluster's node at `--add-machine`; `--cilium-values` (designed in 1.2, step 3) now carries the operator's values into a takeover of a Cilium with no release record; the non-Cilium refusal says Ichor does not migrate a CNI.

## Amendment 2026-11-14: the encrypted-disk warning after a reset

Decided: the reclaim request bullet no longer names what an encrypted disk's key depends on. It says only that after the reset (STATE and EPHEMERAL) the data on an encrypted disk may be unreadable. The request itself is unchanged.

## Amendment 2026-11-14: the mechanism of the encrypted-disk warning

Decided: the warning now names the mechanism. It is read from Talos v1.14.5 (`internal/app/machined/pkg/controllers/block/volume_manager.go`, `internal/pkg/encryption/keys`, `internal/pkg/partition/helpers.go`) and go-blockdevice v2.0.32 (`encryption/luks/header.go`, `block/wipe_linux.go`).

- **Where a LUKS2 key lives.** The volume's header, its two binary headers and the JSON metadata that names its keyslots and tokens, sits at the start of the encrypted partition, and the header is read from offset 0. The reset's wipe of a partition zeroes its first and last 1 MiB and discards it (the discard may or may not zero). A partition wiped that way has lost its header, so it cannot be opened whatever the key. Whether any keyslot material beyond the first MiB survives is not established, and the warning says nothing about it.
- **`nodeid` keys.** The key is the system UUID from SMBIOS (or a `MetaKey` UUID override) with the volume's ID, its `VolumeConfig` ID, not a filesystem label. It does not depend on `STATE`. The default reset names only `STATE` and `EPHEMERAL`, so it changes neither input.
- **`lockToState` keys.** The wrapper applies to any key type. It appends the `EncryptionSalt` that Talos keeps in a file on `STATE`. The reset deletes that file and the node writes a new salt, so a `lockToState` key cannot be rebuilt. Only those keys become unreproducible after a `STATE` wipe.
- **Left open.** The TPM and KMS handlers across a reset, and whether a keyslot survives beyond the first MiB. The warning does not claim either way.

The CLI row, the reclaim guide and `reclaim.Volume.Encrypted` say the same thing.
## Amendment 2026-11-15: adopt takes Talos v1.14 and later

The floor for `ichor adopt` is now Talos v1.14 or later, which replaces the v1.12 floor in the decision above and in the body: adopt takes a cluster whose version contract is v1.14 or later, and refuses an older one before anything is written. The reason is that Ichor turns sign-in on by default and only v1.14 carries its issuer (ADR 0094's amendment of the same date). The refusal names the upgrade (`ichor upgrade talos`) and then adopt again. The probe floor in the code (`adoptMinTalos`) stays v1.12, since it only chooses among contracts; the refusal is applied to the contract the probe chooses.
