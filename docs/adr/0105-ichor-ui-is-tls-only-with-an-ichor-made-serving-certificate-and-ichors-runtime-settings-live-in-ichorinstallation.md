# 0105. ichor-ui is TLS-only with an Ichor-made serving certificate and a CA the edge can verify, and Ichor's own runtime settings live in `IchorInstallation`, editable from a Settings tab

Status: Accepted; built · Date: 2026-10-29 · Design section: Trust, Deployment, CLI and UI · Extends: 0059, 0094, 0100, 0104 · Touches: 0065, 0103 (reclaim)

Decided: ichor-ui never serves plaintext to the network: it listens for HTTPS only on a new port 8443, with the certificate the operator supplies (`ichorUI.tls.secretName`, for example a cert-manager Secret) or, when none is supplied, a leaf from the Ichor CA that the controller already keeps for the 8444 issuer listener (`ichor-oidc-ca`, `ichor-oidc-tls`), issued for every install and not only with users enabled; the controller publishes that CA, public part only, as a ConfigMap and a Secret named `ichor-ui-ca` so an Ingress-NGINX, a Gateway API `BackendTLSPolicy` or a client holding `--ca-file` can verify the backend, while a plain L4 load balancer needs the operator's own certificate; an edge re-encrypts to ichor-ui; the kube-apiserver's 8444 fetch is unchanged and keeps the Ichor leaf even when the operator supplies a certificate for 8443; an existing install's plaintext listener on 8080 is closed in the same release and the installer moves that install to 8443 TLS; certificate hot reload is the work of ADR 0094's amendment and is used here, not redesigned; Ichor's runtime settings are new optional fields of the existing singleton `IchorInstallation` (not a new kind), live-read by the controller, the webhooks and ichor-ui, edited from a Settings tab and by `ichor settings`, guarded by RBAC verbs checked in the webhook; a Helm install gets an `IchorInstallation` too, created once by the controller if absent, and a new field `spec.deployment.manager` (`installer` or `helm`) is how `ichor upgrade ichor`, the UI, the webhook and ADR 0104's `ichorPresent` tell the installer Job path from Helm

## Context

ichor-ui is highly privileged: it holds a read-only Talos identity, impersonates users against the Kubernetes API, is Ichor's OIDC issuer (ADR 0094) and carries the override reclaim form (ADR 0103). Today:

- `cmd/ichor-ui/main.go` serves plain HTTP on 8080 unless `--tls-cert-file`/`--tls-key-file` are given; with them it calls `srv.ListenAndServeTLS`, which reads the pair once and never again. `docs/guides/users-and-login.md` ("Expose ichor-ui over https") tells operators to put TLS "at the edge", which leaves edge to pod in cleartext.
- The 8444 listener already has the machinery this decision needs: the `IssuerTrustReconciler` (`internal/controller/issuer_trust.go`) keeps a 10 year CA in `ichor-oidc-ca` and a one year leaf in `ichor-oidc-tls` (SANs: the Service ClusterIP and `<service>.<ns>.svc`), renews at two thirds, and publishes the public parts in `ichor-oidc-trust` (key `ca.crt`). But it is started only with `--user-issuer` (`cmd/main.go`), so an install without users has no CA.
- `ichorUI.tls.secretName` (chart) and `--ui-tls-secret`/`--ui-tls-cert` (`ichor init`) mount a Secret at `/etc/ichor/tls`; `internal/installer` (`CustomizeUI`, `ReadUISettings`) re-applies that on every upgrade (ADR 0059 amendment).
- Ichor's own settings are command-line flags on the controller (`--reclaim`, `--no-cilium-policies`, `--user-issuer`) and on ichor-ui (`--token-ttl`, `--refresh-lifetime`, `--external-url`). Changing one means editing a Deployment, which `ichor init` and the installer own, and which a Helm release owns on a Helm install. There is no Settings page.
- `IchorInstallation` (`api/v1alpha1/ichorinstallation_types.go`) is the cluster-scoped singleton named `ichor` with `spec.version` and `spec.installerRepository`; `ichor init` creates it. ADR 0104 decision 4.3 says a Helm-installed Ichor has none and that `ichorPresent` (IchorInstallation, or a deployed Helm release of the chart, or the controller Deployment) must tolerate that.

Library facts (controller-runtime v0.24.1): `pkg/certwatcher.CertWatcher` offers `New`, `WithWatchInterval`, `RegisterCallback`, `GetCertificate`, `Start`; `webhook.Server` already builds a `certwatcher` and sets `GetCertificate` whenever `TLSOpts` does not set one (`pkg/webhook/server.go`), so the webhook already follows its certificate. The metrics server and the 8444 listener read the key pair on every handshake (`lazyKeyPair`, `internalServer`); only ichor-ui's main listener and `ListenAndServeTLS` do not follow rotation.

## Decisions

### Part A. TLS to ichor-ui

**1. ichor-ui has no plaintext mode.** One listener serves the SPA, the RPC API, `/metrics` and the probes, on port **8443**, HTTPS only. The listener starts even when no certificate exists yet and answers every handshake with an error until one does (the readiness probe, an HTTPS `httpGet`, keeps the pod out of the Service); it never falls back to HTTP. The flags `--tls-cert-file` and `--tls-key-file` stay and now mean "the operator's pair". New flags: `--tls-dir` (default `/etc/ichor/ui-tls`, the managed pair). `--addr` defaults to `:8443`. Rejected: **keeping a `--insecure` escape hatch for development** (a flag that disables the control is the first thing a copy-pasted manifest carries; development uses the managed certificate and `--ca-file`); **same port 8080 serving TLS** (every probe, Service, NetworkPolicy, port-forward and bookmark would silently change meaning, and a client that still speaks HTTP gets a confusing TLS error; a new port makes both versions coexist, decision 6); **mTLS between edge and backend** (the edge proxies for browsers and cannot present a client identity ichor-ui could map to anything; the user is authenticated by the OIDC token inside the request).

**2. Which certificate.**

| Operator supplies | 8443 serves | 8444 serves |
|---|---|---|
| a Secret (`ichorUI.tls.secretName`, `--ui-tls-secret`, cert-manager) | the operator's pair from `/etc/ichor/tls` | the Ichor leaf |
| nothing | the Ichor leaf, from `ichor-oidc-tls` mounted at `/etc/ichor/ui-tls` | the Ichor leaf |

The Ichor leaf gets more SANs than today: the Service ClusterIP, `<svc>.<ns>.svc`, `<svc>.<ns>.svc.cluster.local`, `<svc>`, `localhost`, `127.0.0.1`, and the host of `--external-url` when users are enabled (so a client given the CA verifies a direct connection through an L4 load balancer; a browser will not trust it, which is the operator-certificate row's reason to exist). The Secret and CA names stay `ichor-oidc-*` (renaming a Secret that an installed apiserver trust chain and the installer's `resourceNames` reference buys nothing); the docs call the pair "the Ichor serving CA". The `IssuerTrustReconciler` splits: the TLS half (CA, leaf, trust ConfigMap, `ichor-ui-ca`) runs for every install; the signing-key and user-credential halves stay behind `--user-issuer`. `--user-issuer` remains a flag with its meaning narrowed to those halves. The pod mounts `ichor-oidc-tls` with `optional: true` so ichor-ui starts before the controller has issued the first leaf; the kubelet populates the volume in place after the pod has started, which can take a minute or more (an optional Secret volume is refreshed on the kubelet's sync period), so the liveness probe is a TCP connect and only the readiness probe is an HTTPS `httpGet`: a pod waiting for its first leaf is kept out of the Service but is not restarted. The reconciler exports the expiry of the CA and the leaf as a metric. Rejected: **a second CA and leaf for the edge-facing listener** (two trust anchors and two renewals for one ClusterIP; the leaf may serve both listeners because the 8444 CA is already pinned only for the apiserver's issuer fetch and trusts nothing else); **cert-manager as a dependency** (ADR 0006 and 0101: Ichor ships no certificate dependency; cert-manager stays an operator choice through `secretName`); **a self-signed certificate generated in the pod at start** (each replica would differ and nothing could publish a CA for the edge).

**3. How the edge verifies the backend.** The controller publishes the CA certificate only (never a key) as the ConfigMap `ichor-ui-ca` and the Secret `ichor-ui-ca`, both with key `ca.crt`, in `ichor-system`, updated on CA change. Service port 8443 is named `https`. The guide gets one recipe each. The Service is `ichor-ui-service` on a Helm install and `ichor-ichor-ui-service` on an `ichor init` install, and the Ichor leaf carries the name of the Service the install has; the recipes use the first name, and the name an edge verifies must be the one the install actually has:

- **Ingress-NGINX**: backend protocol HTTPS, `proxy-ssl-verify` on, `proxy-ssl-secret: ichor-system/ichor-ui-ca`, `proxy-ssl-name`/server name `ichor-ui-service.ichor-system.svc`. `proxy-ssl-name` is required: without it nginx checks the name `upstream_balancer` and the handshake fails. A Secret holding only `ca.crt` is accepted as `proxy-ssl-secret`, so `ichor-ui-ca` is used as it is. The Ingress lives in `ichor-system`, because it must reference the Service.
- **Gateway API `BackendTLSPolicy`**: `targetRefs` the ichor-ui Service, `validation.caCertificateRefs` the ConfigMap `ichor-ui-ca`, `validation.hostname` `ichor-ui-service.ichor-system.svc`. Needs a Gateway API release that serves `BackendTLSPolicy` at the cluster's version; the guide states which and falls back to the Ingress recipe's equivalent for the implementation in use. Envoy applies a changed or wrong CA only to new upstream connections, so a CA change shows on the next connection, not on one already pooled.
- **Plain L4 load balancer** (`Service` type `LoadBalancer`, or TCP passthrough): the load balancer terminates nothing, so clients see ichor-ui's certificate and the host name they typed. Use the operator-certificate row. With the Ichor leaf only clients given `ichor-ui-ca` (`ichor --ca-file`) verify.
- An L7 cloud load balancer that cannot verify its backend is out of scope; the guide says "use a controller that can".

**4. The 8444 fetch.** Unchanged in shape: the kube-apiserver reads `https://<ClusterIP>:8444/.well-known/openid-configuration` and verifies it with `ichor-oidc-trust`'s CA (ADR 0094). What changes: the listener and 8443 share the reload helper of ADR 0094's amendment, so a renewed leaf is served by both; the NetworkPolicy of ADR 0100 gains ingress on 8443 (the rule that listed 8080) and keeps 8444 for `kube-apiserver`. Port 8444 is never routed by an edge (the guide already says so; the policy enforces it for Cilium installs).

**5. Hot reload.** Not designed here. ADR 0094's amendment (`certwatcher`) makes ichor-ui's listeners, the webhook and the metrics server follow their certificate files without a restart. This ADR depends on it for the main 8443 listener and for the cert-manager case (`secretName` Secrets are mounted, so a cert-manager renewal reaches the pod through the kubelet's Secret volume sync and then the reload; most of the delay is the kubelet's copy of the Secret, up to about a minute).

**6. Migration of an existing install.** This change serves 8443 TLS and no plaintext; the amendment of 2026-10-30 removed the transitional 8080 listener this decision first planned for one more minor release.

| Existing install | Result |
|---|---|
| plain HTTP on 8080 (no `--tls-cert-file`) | moved to 8443 TLS (Ichor leaf); 8080 is closed and the Service has no `http` port; the installer prints a notice naming 8443 and `ichor-ui-ca`; `--http-addr` is a deprecated no-op for one release |
| TLS on 8080 with the operator's Secret | `--addr` pinned to `:8080` by the installer (it already reads `--tls-cert-file` from the live Deployment, `ReadUISettings`), nothing moves; 8443 is not added; it gains the reload |
| fresh `ichor init`, fresh `helm install` | 8443 TLS only, no plaintext |

The installer derives the case from the live Deployment as it already does and never needs a new state store (ADR 0059 amendment). `ichor ui` (port-forward) and the CLI use 8443 and `https://localhost:<port>` with the CA fetched from `ichor-ui-ca` (the kubeconfig already grants the read), and stay on 8080 while `ichor-ui-ca` is missing.

### Part B. Settings

**7. Settings live in `IchorInstallation`, as new optional fields; there is no new kind.** The singleton already exists on every `ichor init` install, is already guarded by a CEL name rule and the webhook, is already read by the CLI, UI and installer, and is already the place "how Ichor itself is installed" is recorded. Added to `spec` (all optional; none removed or renamed; defaults keep today's behaviour):

```text
spec.deployment.manager      installer | helm      (omitted = installer)
spec.reclaim.enabled         *bool                  (override, ADR 0103)
spec.users.tokenTTL          duration, 1m..1h       (ADR 0094)
spec.users.refreshLifetime   duration, 1h..720h
spec.defaults.driftPolicy    enforce | warnOnly     (a new TalosCluster's default)
```

Initial scope is what is read cheaply at run time and has no Deployment shape: `reclaim.enabled` (the controller and the reclaim webhook read the setting per call instead of a startup bool), the two user lifetimes (ichor-ui reads them per issued token from its cache), and the default drift policy (the existing defaulting webhook fills `TalosCluster.spec.driftPolicy` at create; an existing cluster is never touched, so the controller still never mutates a spec). Further settings are added as optional fields in later ADRs; each must be live-readable.

Precedence: a set field wins; an unset field falls back to the flag or chart value, so a Helm install without any `spec.*` field behaves exactly as before. `status.effective` (written by the controller; ichor-ui reports its own two values over the Settings RPC) shows each value and its source (`spec` or `deployment`), and the condition `SettingsApplied` shows the controller has seen the generation. A deployment that wants settings owned by Git or Helm sets the controller flag `--settings-read-only` (chart `settings.readOnly`): the webhook then denies writes to the settings fields, every consumer ignores them, the Settings tab is read-only with a "managed by the deployment" Alert. No live-reload gap is accepted: a change takes effect on the next call (ichor-ui and webhook within the informer's delay); nothing in settings needs a rollout. Deployment-shaped values (images, replicas, resources, the TLS Secret name, `externalURL`, the Cilium-policy opt-out, which are applied by objects Ichor does not render at run time) stay with the installer and Helm and appear on the tab as read-only facts (TLS: source, subject, expiry; Ichor version; manager).

Rejected: **a new cluster-scoped `IchorSettings` kind**. It would give settings their own RBAC and their own lifecycle, but: every consumer, the CLI, the installer (CRD list in `resourceNames`, `TestInstallerRBAC`), the chart and the snapshot would learn a second singleton whose existence must be handled in the absent case on top of the first; the Helm question (who creates it) is the same question and is answered once for `IchorInstallation` below; and the one real benefit, splitting edit rights, is available on one object with the webhook pattern ADR 0094 already uses (decision 9). Rejected: **a ConfigMap** (no schema, no CEL, no printer columns, no typed UI). Rejected: **flags only, with the UI patching Deployments** (the UI would write objects it does not own and the installer or Helm would revert the edit). Rejected: **putting settings on `TalosCluster`** (they are installation-wide, not per cluster; the default drift policy is the one per-cluster fact and is a default there).

**8. A Helm install gets an `IchorInstallation`, and `spec.deployment.manager` says who deploys.** The chart does not render it: a rendered object would be overwritten by `helm upgrade`, reverted by a GitOps tool tracking the release, and would invite the installer to fight Helm (the reason ADR 0104 4.3 skipped it). Instead the controller, on start and only when the singleton does not exist, **creates it once** with `spec.version` = its own version and `spec.deployment.manager` taken from a new flag `--deployed-by` (`helm` rendered by the chart; `installer` is the default and what `ichor init` writes itself). It never updates `spec` afterwards. This is a narrow, stated exception to "the controller never mutates `spec`": creating a missing singleton with computed defaults changes no user intent, and nothing is lost if it fails (every consumer tolerates absence, as 0104 required). The alternative that keeps the rule whole, the first save in the Settings tab creating the object, was rejected: the version and manager would then be unknown until someone saved, and `ichor upgrade ichor` could not tell Helm from the installer on a cluster nobody has opened the tab on.

For `manager: helm`: `spec.version` records the version at creation and is not compared with the running controller (`UpToDate` is `True` with reason `ManagedByHelm`, the UI's "Update available" badge and `OperationService.GetIchorInstallation`'s `update_available` are suppressed); the validating webhook denies a `TalosOperation` of kind `ichor` (message: "this Ichor is installed by Helm; run helm upgrade"), the executor and the installer Job refuse as a second line, and the chart's `installer.enabled` stays false. `ichor upgrade ichor` reads the field first and prints the Helm command. `ichor upgrade ichor` on a Helm install exits non-zero with ``ichor is installed by Helm (release "ichor", namespace ichor-system); upgrade it with `helm upgrade ichor oci://ghcr.io/maeshinshin/charts/ichor --version VERSION --namespace ichor-system`, not with the installer`` and creates no `TalosOperation`. The Settings tab shows "Installed by Helm" and still edits runtime settings, which Helm does not render; a settings edit lives in `spec` of an object the chart never renders, so it survives `helm upgrade`.

**`ichorPresent` with a seeded object.** `ichorPresent` is unchanged in its three signals (IchorInstallation, deployed Helm release of the chart, controller Deployment) because the first two windows remain: before the controller seeds, and on installs older than this ADR whose controller has not yet been upgraded. What changes: (a) when the singleton exists, `spec.deployment.manager` is authoritative over the other two; (b) adopt skips the install step on `manager: helm`, creates no `IchorInstallation` itself (the controller does) and, when the object is still absent, does not wait for it; (c) installer-Job commands refuse on `manager: helm` and, while the object is absent, on a Helm release; (d) code that needs the object tolerates its absence in the seed window; the chart still never renders it. `GetIchorInstallation`, the CLI skew check (`status.installedVersion` is still written by the controller) and the PR-mode editor of ADR 0059 amendment 4 (it edits only `spec.version` in a tracked file, so a tracked `manager: helm` object is simply refused there) tolerate both an absent and a seeded object.

**9. RBAC, validation, audit.** Reading is part of `ichor-viewer` (the spec holds no secret and the page shows no secret). Writing `ichorinstallations` stays `ichor-admin`'s; the finer split uses the webhook pattern of ADR 0094 (a `SubjectAccessReview` on the request's user): changing `spec.version` or `spec.deployment` needs the verb `update` on `ichorinstallations/version`, changing `spec.reclaim` needs `update` on `ichorinstallations/reclaim`, and everything else under `spec.users`/`spec.defaults` needs `update` on `ichorinstallations/settings`; the built-in `ichor-admin` role holds all three on separate rule lines so a custom role can hold fewer. `spec.reclaim.enabled: true` additionally requires the typed confirmation (the UI's dialog; the CLI's `--confirm-reclaim`) that the API enforces by an annotation the request must carry (`ichor.maesh.dev/confirm-reclaim: enable`), so a stray `kubectl apply` cannot turn override on by accident. Validation is CEL on the CRD (duration bounds, `tokenTTL <= refreshLifetime`, the enums, the name rule that exists) plus the webhook for the SAR checks and `--settings-read-only`. Audit: the Kubernetes audit log names the user (ichor-ui impersonates, ADR 0058), and the webhook emits an Event on the `IchorInstallation` per accepted change listing the changed field paths, old and new values (none is secret by construction) and the user; enabling reclaim also emits the Warning event ADR 0103 already defines for its use.

**10. UI and CLI.** A "Settings" entry in the sidebar, a page of stock preactcn components: `Tabs` (General, Sign-in, Override, Defaults), `Card` with `CardHeader/Title/Description`, `Field`, `Input`, `Select`, `Alert` (managed by Helm or the deployment), `Badge` (source: spec or deployment), `AlertDialog` (reclaim confirmation), `Button`. `Switch` is not in `ui/src/components/ui` yet; it is added with `npx shadcn@latest add @preactcn/switch`, never by hand. English strings in `ui/src/lib/i18n.ts`. A new `SettingsService` (Get, Update) in the UI API; Update is a merge patch of the settings fields only, as the user. CLI: `ichor get settings` and `ichor set settings KEY=VALUE...` write the same CR.

## Risks

- A breaking edge: an operator whose edge speaks plain HTTP to 8080 loses the UI on the upgrade that closes it. Mitigated by the installer's notice naming 8443 and `ichor-ui-ca`.
- Readiness depends on the controller having issued the leaf; a controller outage at first install leaves ichor-ui unready (it was ready with plaintext). `ichor init` already bounds its waits and names the reason (ADR 0104).
- A seeded object is created by a component that otherwise only reads `spec`; a bug there would hide behind "absent is fine". Create-only.
- Anything that reads settings live widens what a mistaken edit can change at once; the three RBAC lines, the confirm annotation and the Event are the compensation, and reclaim stays default off.
- Browser trust: the managed leaf is not browser-trusted. This is intended (the edge presents the public certificate) but a user on L4 passthrough must read the guide.

## Open questions

1. Rotation of the Ichor CA itself with an overlap period (publishing two CAs in `ichor-ui-ca` and the apiserver's `certificateAuthority`); today the CA is replaced when near its end and everything re-trusts at once. Not needed for this change, needed before the 10 year mark.
2. Whether the ichor-ui login settings (`--oidc-*`, the external IdP) should become runtime settings too; they need a provider re-discovery path and are left to a later ADR.

## As built (2026-10-29)

Differences from the text above (the build is right):

- **Settings page**: stock `Card`s, not `Tabs` (General, Sign-in, Override, Defaults became cards: Deployment, Override reclaim, Sign-in, Defaults). `Switch` was added with `npx shadcn@latest add @preactcn/switch`.
- **No "unset"**: neither the UI nor `ichor settings` can clear a field once set; a field set stays set. Precedence is as designed for fields never set.
- **`defaults.driftPolicy`** is `warnOnly | autoCorrect` (the enum of `TalosCluster.spec.driftPolicy`), not `enforce | warnOnly`.
- **TLS on 8080**: the installer pins a live `--addr` other than 8443 on a TLS install to its value. The chart has no automatic detection; `ichorUI.port` keeps a former 8080 TLS install in place.
- **CLI trust**: `ichor ui` and the API client stay on 8080 while `ichor-ui-ca` is missing.
- **Helm denial**: the denial of `kind: ichor` on `manager: helm` lives in the `TalosOperation` validating webhook; the installer refuses by reading the live Deployment, as a second line.
- **Drift default**: the CRD default of `TalosCluster.spec.driftPolicy` was removed in favour of a create-time defaulting webhook (`failurePolicy: Ignore`; an empty value is read as `warnOnly`, so a down webhook changes nothing). The installer's RBAC gained `mutatingwebhookconfigurations`. The CRD field itself is kept (CRD fields are append-only).
- **Token lifetime**: `users.tokenTTL` is capped at 1h (`MaxTokenTTL`), as the CEL rule says.
- **Monitoring**: the ServiceMonitor verifies the HTTPS port against `ichor-ui-ca` (`ichorUI.tls.caConfigMap/caSecret/caKey`) and never skips verification.
- **Reload**: certificates reload on change through `certwatcher` (ADR 0094 amendment, built).
- **Docs**: the Ingress-NGINX recipe uses `backend-protocol`, `proxy-ssl-verify`, `proxy-ssl-secret` (`namespace/name`), `proxy-ssl-name` and `proxy-ssl-server-name`; the reference describes `proxy-ssl-secret` as holding a client pair that "should also contain" `ca.crt`, yet a Secret with only `ca.crt` is accepted as the trusted CA. `BackendTLSPolicy` is `gateway.networking.k8s.io/v1`, Standard channel since Gateway API v1.4, same namespace as the Service, `ca.crt` ConfigMap as Core support. The guide for settings is `docs/guides/settings.md`.

## Amendment 2026-10-30: the transitional plaintext listener is removed in the same release

The transitional plaintext listener is removed now instead of in the next minor release. As built:

- **ichor-ui**: the plaintext server is gone. `--http-addr` stays as a deprecated no-op for one release (flags are an interface): a hand-edited Deployment that still passes it starts and logs `--http-addr=... ignored: plaintext was removed (ADR 0105)`. Delete the flag in the release after.
- **Installer**: `ReadUISettings` no longer produces a plaintext listener. A plaintext install (live `--addr` other than 8443, or a leftover `--http-addr`) is moved to HTTPS on 8443; the Service has no `http` port and the policy opens only 8443. `UISettings.WasPlaintext` records the old address and drives the notice "ichor-ui no longer serves plain HTTP; point your edge at https://<ichor-ui>:8443 (trust ichor-ui-ca)". A TLS install on 8080 is still pinned to 8080 (and its policy port opened). The installer no longer strips or re-adds `--http-addr`; it deletes it from the live args.
- **Chart**: `ichorUI.plaintextPort` is removed. An old values file that sets it is ignored by Helm and renders no plaintext port.
- The Settings and Overview Alert about plain HTTP that decision 6 first planned is not built.

## Amendment 2026-10-30: the stale `http` Service port of an `ichor init` install is removed

Fixes a stale `http` 8080 port left on the ichor-ui Service of an `ichor init` install after the plaintext removal. The cause was general: `ichor init` created every object of Ichor's manifest with `Create` (field manager `ichor`, operation `Update`), and the installer's server-side apply as `ichor-installer` cannot remove a list item (or any field) another manager owns, so anything a release drops from the manifest stayed on an init-made install.

- **Installer.** Before it applies any object other than a Deployment, `applyOne` reads the live object and, if manager `ichor` holds `Update` entries, hands those fields to `ichor-installer` with `k8s.io/client-go/util/csaupgrade` (`UpgradeManagedFieldsPatch`, the documented client-side to server-side upgrade; the patch guards on the resourceVersion) and logs it. The apply then owns the whole object it knew and drops what the manifest no longer has: the `http` 8080 port of the ichor-ui Service, and equally a dropped field on a CRD, ClusterRole, ConfigMap or CiliumNetworkPolicy. Fields set by other managers (an operator's `kubectl edit` port) are untouched. Deployments need nothing: the installer replaces them whole.
- **Objects affected** (all objects `ichor init` creates from the manifest except Deployments): in practice only the Service had a dropped item on this upgrade; the others had no fields removed, but the same hand-over now protects them on later releases.
- **`ichor init`.** New installs create every non-Deployment object with a server-side apply as `ichor-installer` (a Deployment is still created, with that field manager). An existing object is still skipped, so re-running init is unchanged. Init's own later `Update`s (the internal port, the Deployment args) remain manager `ichor`, and the next upgrade hands them over like any older install.
- **Docs.** `docs/guides/users-and-login.md` named the Service `ichor-ui-service` where an `ichor init` install has `ichor-ichor-ui-service`; the certificate-names bullet is corrected.

## Amendment (ADR 0107)

`spec.reclaim.enabled`, the `ichorinstallations/reclaim` subresource, the confirmation annotation and the Settings reclaim card are gone: the field is deprecated and ignored, and "Reset and add" is decided by the `reclaim` verb on `machinereclaims` alone.

## Amendment (2026-10-30): an upgrade hands the leader lease over

The Secrets are issued by the controller leader (`IssuerTrustReconciler`, event driven, it runs once at start). After an upgrade the new controller pod was not the leader: `LeaseDuration` is 120 s (ADR 0063) and the old pod did not release the lease when it stopped, so the new one waited out the lease before issuing `ichor-oidc-ca`, `ichor-oidc-tls` and `ichor-ui-ca`. The manager now hands the Lease over itself after a plain voluntary stop (ADR 0063 amendment of 2026-10-30), so an upgrade hands over at once; after it the remaining wait is the kubelet copying the new Secrets into ichor-ui's volume, up to about a minute (an optional Secret volume is refreshed on the kubelet sync period). A crash, or a stop that goes into the etcd restore tail, still waits out the lease.

## Amendment (2026-11-03): an operator's certificate does not stop in-cluster clients verifying ichor-ui by its Service name

`ichor upgrade ichor` warned that ichor-ui's certificate could not be verified and computed the plan from the Kubernetes API. An install can supply its own certificate for the load balancer's address (`init --ui-tls-cert`), so 8443 served only that certificate. The CLI dials the port-forward with the Service name (`<service>.<namespace>.svc`) and verifies against `ichor-ui-ca`, which is Ichor's CA: the operator's certificate has neither the name nor that CA. Ichor's own leaf, which has the name, stayed on disk beside the operator's pair (`/etc/ichor/ui-tls`, mounted by the chart and by the installer), but no handshake was ever answered with it.

Decision: ichor-ui serves the Ichor-made leaf to a handshake whose SNI is a Service DNS name (`*.svc` or `*.svc.cluster.local`) that the leaf covers, and the operator's pair to every other handshake: an external name, an address, or no SNI. The CLI and in-cluster clients keep verifying the Ichor leaf against `ichor-ui-ca`; no client gets a new trust anchor. The Ichor leaf names the Service as `<name>`, `<name>.<namespace>`, `<name>.<namespace>.svc` and `<name>.<namespace>.svc.cluster.local`, plus `localhost` and the external host (the names the controller already put there, now with the `<name>.<namespace>` form). Adding a SAN makes the controller reissue the leaf once.

Rejected: the CLI trusting the operator's certificate (it has no in-cluster way to learn its CA or its names, and a self-signed certificate for an address needs `--ca-file` and `--tls-server-name` on every command); publishing the operator's CA as `ichor-ui-ca` (the controller does not hold that CA and the ConfigMap is the Ichor CA by name); a second in-cluster port (the 8444 listener serves only the issuer's discovery and key set).

The fallback is unchanged in shape and stays for real failures: an unreachable ichor-ui, or a certificate that does not verify even by Service name (for example after a CA rotation the ConfigMap has not caught up with). The warning no longer appears for a healthy ichor-ui with an operator certificate.

Consequences: an edge that verifies the backend by the Service name still needs Ichor's CA (`ichor-ui-ca`), as before; an edge with an operator certificate verifies that certificate for its external name. The first `ichor upgrade` run with a CLI from this change still uses the old ichor-ui and so still warns; later commands are verified once the upgraded ichor-ui serves.
