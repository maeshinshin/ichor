# 0108. Security hardening

Status: Accepted; built; the five items it deferred as follow-ups are all built since (ADR 0120 to 0127, see the amendments after "Follow-ups") · Date: 2026-11-02 · Design section: Trust, Deployment, Nodes · Touches: 0011, 0041, 0058, 0063, 0089, 0103, 0105, 0107

Decided: Ichor is hardened area by area after five read-only audits (2026-11-02): ichor-ui and its auth, the controller's privileges and admission, workloads and the supply chain, the security of the clusters Ichor creates, and secrets and credentials. Fixes to Ichor itself are made directly. For the clusters Ichor creates, every new hardening is a typed option that is off by default, for new and existing clusters alike; disk encryption stays opt-in (the user's decision, 2026-11-02). Each area below records its decisions and what was built.

## Context

The user asked for security to be hardened "to the extreme" (2026-11-02). Five audits read the code and manifests and listed findings with file:line evidence, an exploit scenario and a fix. Asked how far new clusters' defaults should go, the user chose that all cluster-side hardening is opt-in, and that disk encryption stays opt-in.

## Admission and confused deputy

The controller does things on a CR author's behalf with rights the author does not have: it pushes a rendered machine configuration (the cluster's CA keys) to a machine, resolves a credential Secret, sends snapshots to an S3 endpoint, and creates Jobs whose ServiceAccounts can create roles. The audit (rbac-admission F1 to F9, secrets S5) found places where the author chose the target or the Secret without the matching right.

### Decisions

1. **A machine's endpoint is an address the cluster declares.** The `TalosMachine` webhook judges `spec.endpoint` on create and whenever the endpoint or `clusterRef` changes (an update that leaves both alone is not judged, so a machine stays editable after its discovery entry goes away). Never allowed, for anyone: an unspecified, loopback, link-local or multicast IP, or one inside the pod or service ranges the cluster declares in `spec.network` (`pkg/endpointguard`). Talos's undeclared defaults (`10.244.0.0/16`, `10.96.0.0/12`) are deliberately not assumed: a cluster's machines may live in those ranges, for example when it runs inside another cluster. Allowed: an address in the cluster's `spec.discovery.addresses` or `cidrs`; any other address needs the new right `update` on `talosmachines/endpoint` (a hostname cannot be classified here, so it needs the right too).
2. **Approving needs a right.** Moving `spec.approvalState` to `approved`, including at creation, needs `approve` on `talosmachines/approval`, asked by SubjectAccessReview as the requesting user like `talosclusters/authentication`. `ichor-operator` and `ichor-admin` hold it (they could approve before, through `update`); `ichor-admin` also holds `talosmachines/endpoint`. The `talosmachine-editor-role` helper holds neither: an editor can no longer approve. `talosmachine-admin-role` holds both.
3. **The controller re-checks before it dials.** `provision()` runs `endpointguard.ForbiddenResolved` on the dial endpoint (including `status.observedEndpoint`, and what a hostname resolves to) before the insecure maintenance probe, and sets `Ready=False` `EndpointRefused` without dialling. It does not require discovery membership: `ichor init` and `ichor adopt` write machines at addresses they were handed, and the controller cannot ask who wrote the CR.
4. **`MachineReclaim.spec.address`** gets the same forbidden classes in the webhook (the cluster's ranges are not known there; the reclaim verb and the foreign talosconfig remain the other gates).
5. **Where credentials go is part of the Secret reference.** A change to `spec.registries[].endpoints` of a registry that keeps its `authSecretRef`, and a change to `spec.destination.s3` endpoint, bucket, prefix, region or the new `insecure`, needs `update` on `<resource>/secret-references`, like the Secret name. A plain `http://` S3 endpoint is refused unless `spec.destination.s3.insecure: true` (new optional field; judged when the endpoint or the flag changes, so a stored `http://` backup keeps working; the controller does not re-check).
6. **Jobs.** Two ValidatingAdmissionPolicies bound to the controller's ServiceAccount (`config/admission/controller-jobs-policy.yaml`, mirrored in the chart): the first allows only the installer Job (`ichor-installer`, in the Ichor namespace, `installer run`) and the Cilium Job (`ichor-cni`, in kube-system, `cni helm apply`), one container, no command override, only `KUBERNETES_SERVICE_HOST`, `KUBERNETES_SERVICE_PORT` and `HOME` as environment, dropped capabilities, no privilege escalation, `emptyDir` volumes only, `hostNetwork` for the Cilium Job only, an `activeDeadlineSeconds` of at most an hour (the installer Job now sets 30 minutes; the Cilium Job already set 25). The second ties the image to `IchorInstallation.spec.installerRepository:version` and does nothing while no IchorInstallation exists (a `parameterNotFoundAction: Allow` skips the binding). The chart adds `admission.jobImageRepository` (default `ghcr.io/maeshinshin/ichor-installer`) for an install without an IchorInstallation; set it to a mirror or empty it. Neither Job uses a hostPath today, so none is allowed. The installer's ClusterRole (`config/rbac/ichor-installer/role.yaml` and the chart's copy) holds `get` on `ichorinstallations`, because the apiserver requires it of whoever creates the `ichor-controller-job-image` policy (its `paramKind`); only `get` is needed, not `list` or `watch`. The installer's rights are kept equal to what the install manifest contains: it can `get` and `create` every kind of the rendered `dist/install.yaml` and `get` the `paramKind` of each policy, so a new kind in the manifest needs the installer to be given its rights first.
7. **Escalation verbs are named.** The installer's `bind` and `escalate` list every ClusterRole and Role of the install manifest (the installer applies its own role first, so a release that adds a role extends the list before using it); the Cilium Job's list the roles the pinned chart creates. `dist/chart` tests compare both lists with `dist/install.yaml` and with the chart as rendered under Ichor's values. Residual: the installer keeps `escalate` on its own role by design (ADR 0059 stage 0), so a compromised installer can still rewrite its role; the Job policy and the `ichorinstallations/version` right are what keep that process from being started with another image.
8. **System namespaces.** No `TalosCluster`, `TalosMachine`, `TalosOperation` or `TalosEtcdBackup` may be created in `kube-system`, `kube-public` or `kube-node-lease`: the cluster lock is a Lease named after the cluster, written with the controller's cluster-wide Lease rights. The leader-election role loses its unused ConfigMap rule. Moving the lock to a Role in the Ichor namespace (audit F5c) is not done.
9. **Finalizers.** The override finalizer check also sees `UPDATE` of `TalosOperation` (the `etcd-restore` and `ca-rotation` finalizers). Every Ichor finalizer is now covered (`machine-removal`, `etcd-restore`, `ca-rotation`).
10. **Smaller.** The controller's cluster-wide `pods delete` is gone; the one direct delete (stale agent pods after an etcd restore) is a Role in kube-system (`config/rbac/pod_restart_role.yaml`). The `*-admin-role` helpers list their verbs instead of `*`, so `override` is never implied. `IchorInstallation` deletion needs the `allow-delete` annotation like a cluster. The kube-proxy switch policy reads its fields behind `has()`. Every webhook has `timeoutSeconds: 5`.

### As built

- `pkg/endpointguard` (`Forbidden`, `ForbiddenResolved`, `InDiscovery`); webhook checks in `internal/webhook/v1alpha1` (`talosmachine_webhook.go`, `machinereclaim_webhook.go`, `override_webhook.go`, `system_namespace.go`); constants `MachineApproveVerb`, `MachineApprovalSubresource`, `MachineEndpointVerb`, `MachineEndpointSubresource` in `api/v1alpha1/talosmachine_gates.go`.
- New CRD field `TalosEtcdBackup.spec.destination.s3.insecure` (optional, append-only).

### Flows that change

- **ADR 0011 (discovery).** Unchanged for discovery-created machines: the endpoint is a declared address. Approving now needs `approve` on `talosmachines/approval`.
- **ADR 0103 (adopt, add by IP, reclaim).** Add by IP and reclaim (the UI API, and `ichor reclaim node --cluster`) add the address to `spec.discovery.addresses` before anything else, and the controller creates the pending machine from it, so the endpoint is declared. `ichor init` and `ichor adopt` write approved machines at addresses outside discovery, so the user needs `approve` and `update` on `talosmachines/endpoint` (`ichor-admin` has both; cluster-admin has everything). Reclaim addresses in loopback, link-local, unspecified or multicast ranges are refused.
- **ADR 0086 (observed endpoint).** Unchanged: `status.observedEndpoint` is written by the controller, and the controller refuses to dial a forbidden one.
- **ADR 0106 (S3 store).** An in-cluster or external store over `http://` now needs `insecure: true`; `https://` is unchanged.
- **ADR 0059 (installer).** An installer Job that is still running after 30 minutes is killed.

## ichor-ui and its auth

Decided and built (audit findings F2 to F18 of the ichor-ui audit; F1, the impersonation scope, is under "Credentials and the ichor-ui identity").

- **Request sizes (F2).** `connect.WithReadMaxBytes` on every handler: 256 KiB, and 1 MiB for the services that carry pasted documents (patches, Cilium values, reclaim's talosconfig). The limit applies to the decompressed message and is checked before the interceptors, so an unauthenticated caller cannot make the pod allocate. The mux caps any body at 2 MiB, the issuer's endpoints at 64 KiB, the internal listener at 4 KiB. Every RPC takes one request message (the streaming ones are server streams), so the limits do not touch streaming.
- **Timeouts (F5).** Main listener: `ReadHeaderTimeout` 10 s, `ReadTimeout` 60 s, `IdleTimeout` 120 s, `MaxHeaderBytes` 64 KiB, and no `WriteTimeout` because `StreamNodeLogs` and the downloads run for minutes; a request body is read within `ReadTimeout`, and a stream is bounded by its token (below). Internal listener (kube-apiserver only): 5 s, 15 s, 15 s write, 60 s idle, 16 KiB headers.
- **Security headers (F4).** One middleware on the whole listener, issuer pages included: CSP (`default-src 'none'`, `script-src 'self'`, `connect-src 'self'`, `img-src 'self' data:`, `font-src 'self'`, `base-uri 'none'`, `form-action 'self'`, `frame-ancestors 'none'`), HSTS one year without preload, `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy: no-referrer`, a minimal `Permissions-Policy`, `Cross-Origin-Opener-Policy: same-origin`. The theme snippet moved from `index.html` to `ui/public/theme-init.js`, so scripts need no `'unsafe-inline'`. **`style-src` keeps `'unsafe-inline'`**: two stock pieces create a `<style>` element at runtime (the Radix select viewport and the sonner shim), and editing preactcn components was ruled out; inline CSS cannot run script, so the residual risk is CSS injection only. With an external OIDC provider the browser itself fetches the provider's discovery document and token endpoint, whose origins are not known to ichor-ui, so `connect-src` widens to `'self' https:` in that case only; scripts stay `'self'`.
- **Token revocation (F6).** `authenticateLocal` compares the token's `iat` with the credential's `notBefore` (same cached read as `mustChange`, 10 s), so RevokeSessions and a password change end tokens already issued, not only refresh grants. `notBefore` has whole-second resolution: a token issued in the same second as the revoke survives it. The UI signs out after its own password change. The kube-apiserver cannot do this check; a token already given to `kubectl` lives out its lifetime.
- **Refresh rotation (F7).** A refresh grant returns a new refresh token and retires the old. State is one entry per live family (`families` in the user's credentials entry, so all replicas agree and RevokeSessions or a password change drops them): the id of the current token and the family's expiry, at most 16 per user. Writes are optimistic-lock patches of the Secret, retried on conflict. Presenting a retired token deletes the family (the owner signs in again) and logs it. Rotation keeps the session's start and expiry, so the absolute lifetime is not extended. A token from before rotation is accepted once and starts a family. A race between two processes refreshing the same token is serialised by the CLI's file lock, so it does not trip reuse detection.
- **Login limits (F8, F9, F10, F11).** Failures are counted per (source, user), so a stranger cannot lock `admin` out; per source with a looser limit (30 free failures, at most 1 min); and per user across sources, where 30 failures in an hour add a 2 s delay to every sign-in of that user and never refuse one. Tables hold 50 000 keys and evict the entries with the fewest failures first, so flooding fresh names cannot push out a slowed key. The source is the TCP peer, or with `--trusted-proxy-cidrs` the rightmost `X-Forwarded-For` address outside the trusted list. Counters stay per replica (a Lease per attempt was too expensive): N replicas give N times the free guesses. `/oidc/authorize`, `/login` and `/token` have a per-source token bucket (20, 10 and 20 per second, bursts 100, 50 and 100). A ticket buys one successful login (a typo may retry). Logins hash on their own argon2 slot with a queue of 8 and answer 503 beyond it; password operations of a signed-in user have another slot, so one cannot starve the other (the memory is the same two slots as before). Behind an L4 load balancer or a NodePort every client reaches ichor-ui from the same source address and shares one failed-login counter, so one stranger's wrong passwords for `admin` slow `admin` down for everyone, and `trustedProxyCIDRs` cannot help without an `X-Forwarded-For`. The options are an L7 proxy that sets `X-Forwarded-For` together with `trustedProxyCIDRs`, `externalTrafficPolicy: Local` (the chart's `ichorUI.service.externalTrafficPolicy`, empty by default), or accepting the slowdown; `docs/guides/users-and-login.md` has the section "Client addresses behind a load balancer". A refresh token does not survive an etcd restore, by design: its state is in a Secret that the restore rewinds.
- **Role grants (F12).** CreateUser and UpdateUser refuse to grant a role the caller does not hold, unless the caller is admin. This is in code, not a ValidatingAdmissionPolicy; an external (OIDC) identity has no Ichor roles and is still gated by RBAC alone.
- **Streams (F13).** A stream gets a deadline at its token's expiry and ends with Unauthenticated ("your sign-in expired"). A disable inside the token lifetime is not seen by a running stream.
- **Errors (F14).** Internal, unknown, data-loss and unavailable errors reach the browser as the code plus a reference; the full error is logged with that reference. Errors the caller caused are unchanged.
- **/metrics (F15).** It stays on the main port but needs a Kubernetes token that may `get` the non-resource URL `/metrics` (the TokenReview and SubjectAccessReview of the controller's secure endpoint). The ichor-ui role gains `create` on `tokenreviews` and `subjectaccessreviews`; the ServiceMonitors send the pod's token; the scraping Prometheus needs the `metrics-reader` ClusterRole. A malformed or unaccepted bearer token answers 401: controller-runtime's metrics filter answers 500 to every authenticator error, so `internal/metricsauth` is that filter with the one error `invalid bearer token` mapped to 401 (an unreachable apiserver is still 500), and both the controller's and ichor-ui's metrics endpoints use it.
- **TLS (F16).** TLS 1.2 or newer, with only ECDHE and AES-GCM or ChaCha20 suites on 1.2 (1.3 suites are fixed by Go), curves X25519 and P-256, on both listeners. The `certreload` mutex is unchanged.
- **Dependencies and keys (F17, F18).** `oras-go` v2.6.2 (govulncheck: no vulnerability reached); `oidctrust` refuses an RSA signing key under 2048 bits.
- **No sign-in (F3).** With neither OIDC nor Ichor users, ichor-ui serves only the procedures in `readOnlyProcedures` (a new RPC is closed until listed; downloads are not listed). `--allow-unauthenticated` (`ICHOR_ALLOW_UNAUTHENTICATED`, chart `ichorUI.allowUnauthenticated`) restores the open mode explicitly; `/auth/config` says `anonymous: readonly|open` and the UI banner shows which. Compatibility: the installer reads a live ichor-ui with no users, no OIDC and no flag as "ran open" and sets the flag with a `NOTICE`, so an upgrade changes nothing; `ichor init` and `ichor adopt` start ichor-ui with the flag, `ichor init` without `--ui-url` prints a warning at the end, and `--ui-url` drops the flag. A Helm upgrade of such an install turns read-only until `ichorUI.allowUnauthenticated=true` is set (the chart prints a note). Making users the `ichor init` default was left out of scope.

Not done here: shared login counters across replicas (documented per replica), a ValidatingAdmissionPolicy for role grants, re-checking a disabled user inside a running stream before its token ends, narrowing the Role's `secrets: get` to names (F19, with the credentials work).

## Credentials and the ichor-ui identity

Findings: S1 (ichor-ui holds every CA private key through `get secrets`), F1/F7 (ichor-ui may impersonate any user and group), F19, S2, S3, S4, S6.

### 1. ichor-ui holds no CA key (S1)

Decided: the controller is the only reader of the secrets bundle. ichor-ui asks it for a credential by creating a `TalosCredentialRequest` (new kind, namespaced next to the cluster, short-lived), and the controller answers in the request's `status`.

- **Channel.** A CR, not a controller-local endpoint: it keeps "the UI changes the world by writing CRs", it is authorised and audited by the Kubernetes API server (the audit log shows who created the request, as the impersonated user, and which purpose), and it needs no new listener, certificate or NetworkPolicy. An endpoint would also have had to trust identity claims made by the caller, which is what the API server already checks.
- **No private key crosses the channel.** The requester generates the key pair in memory (Ed25519) and sends a PKCS#10 CSR in `spec.csr`. The controller checks the CSR signature (proof of possession), discards its subject and SANs, builds the subject from the purpose, signs with the CA, and writes the certificate and the CA(s) to trust into `status`. A reader of the request sees only public data. Nothing is written to a Secret, so ichor-ui needs no `get secrets` for credentials. The controller deletes a request 2 minutes after it was created.
- **Purposes** (`spec.purpose`) and the Kubernetes check the validating webhook makes with a SubjectAccessReview as the requester (new file `internal/webhook/v1alpha1/credentialrequest_webhook.go`; the other webhook files are untouched):

  | purpose | certificate | default TTL, cap | SAR as the requester |
  | --- | --- | --- | --- |
  | `public` | none; returns the cluster ID and the CA certificates | n/a | `issue` on `talosclusters/public` (ichor-ui's ServiceAccount) |
  | `node-reader` | Talos `os:reader`, signed by the current OS CA | 10 min, 15 min | `issue` on `talosclusters/node-reader` (ichor-ui's ServiceAccount) |
  | `support-bundle` | Talos `os:reader` | 10 min, 15 min | `download` on `talosmachines/support-bundle` (the signed-in user) |
  | `etcd-snapshot` | Talos `os:etcd:backup` | 10 min, 15 min | `download` on `talosmachines/etcd-snapshot` |
  | `packet-capture` | Talos `os:operator` | 10 min, 15 min | `download` on `talosmachines/packet-capture` |
  | `credentials-talos` | Talos `os:admin` or `os:reader`, signed by the rotation's new OS CA during a rotation, trust = old + new | 365 d, 365 d | `download` on `talosclusters/credentials` |
  | `credentials-kubernetes` | `admin` in `system:masters`, same rotation rule | 365 d, 365 d | `download` on `talosclusters/credentials` |

  The verbs on the download rows are the ones ADR 0084 and 0093 already use, so installed bindings keep working. The two `issue` rows are new and granted only to ichor-ui's ServiceAccount; they are for the UI's own reads (node pages, logs, effective configuration), which today already run as the ServiceAccount after the caller proved `get` on the machine. A request that fails the SAR is denied at admission and never reaches the controller; the controller re-checks purpose, TTL cap and CSR itself.
- **Who creates it.** The three download purposes and `credentials-*` are created as the signed-in user (impersonation), so the SAR and the audit log name that user. That needs plain `create` on `taloscredentialrequests`: every shipped role that holds a `download` verb carries it and the webhook is the gate. `public` and `node-reader` are created as ichor-ui's ServiceAccount. ichor-ui caches the `node-reader` credential (one per cluster, in memory, renewed after half its TTL) and the `public` data (1 minute).
- **ichor-ui's Role** (namespace of the controller) loses `get` and `create` on all Secrets. What remains is by `resourceNames`: `ichor-user-credentials` (get, patch, update; Ichor users) and the issuer's own Secrets that it reads by name. The one `create` that stays is the MachineReclaim credential Secret, narrowed by the existing ValidatingAdmissionPolicy. The bundle Secret, S3 and registry Secrets are no longer readable by it. Where ichor-ui needs a rendering (effective configuration, CNI facts) it renders with a placeholder bundle whose keys are random and whose public parts (cluster ID, CA certificates) come from `public`; every secret field is masked in the output anyway.
- **Residual risk, stated.** A compromised ichor-ui can no longer exfiltrate a CA key, mint certificates offline, outlive a CA rotation, or forge Talos identities beyond a 15 minute window. It can still ask the controller for what the identity it acts as may ask for. With users off that is the ServiceAccount (no download verbs by default); with users on, it can only impersonate Ichor users (section 2) and each purpose is checked against that user's RBAC.
- CRD change: a new kind only; no existing field is touched.

### 1a. What was built, and where it differs from the first design

- `TalosCredentialRequest` (`api/v1alpha1/taloscredentialrequest_types.go`; scaffolded with kubebuilder), its reconciler (`internal/controller/taloscredentialrequest_controller.go`), the signing code (`internal/credentials/issue.go`: `NewCSR`, `IssueTalos`, `IssueKubernetes`, `PurposeLifetime`, `TalosRoles`) and the webhook (`internal/webhook/v1alpha1/credentialrequest_webhook.go`, a new file; registered in `cmd/main.go` and the chart's webhook list).
- ichor-ui: `internal/uiapi/credissuer.go` (create the request, poll its status with the ServiceAccount, cache the reader identity and the public facts). The Talos client factories take a `*TalosIdentity` (CA, certificate, key) instead of a bundle; `loadBundle` is gone. `GetMyKubeconfig` takes the Kubernetes CA from `public`.
- **Registry credentials.** Rendering the effective configuration read the registry `authSecretRef` Secrets by name, which would have kept `get secrets` on the whole namespace. The backend now renders through `maskedSecrets`, which answers every Secret read with a placeholder: the view shows them masked anyway. The cost: a missing or malformed registry Secret is no longer noticed in that view (the controller still reports it on the machine).
- **Acknowledging a CA rotation's credentials** checks that the new Kubernetes CA is accepted with a certificate of purpose `credentials-kubernetes` that lives ten minutes, asked as the caller. That needs the `download` verb on `talosclusters/credentials`, which acknowledging did not need before (it needed only to update the operation). The alternative, a purpose the backend could ask for as itself, would have let a compromised backend obtain a cluster-admin certificate at will, which is what this change removes. The UI shows the download and the continue buttons together to the people who hold the verb; the CLI path (`ichor create credentials --acknowledge`) is unchanged.
- **Roles.** The `ichor-credentials-role` and `ichor-diagnostics-role` ClusterRoles also carry `create` on `taloscredentialrequests`; the webhook is the gate, so plain creation is harmless. `ichor-admin` also holds `create` on `taloscredentialrequests`, because it holds every `download` verb and the user's own request is created as that user. For the etcd backups, the operator and the admin hold `patch` and `update` on `talosetcdbackups` (`ichor backup etcd` sets an annotation) and the admin `create` and `delete` (defining a backup). Flows that need `secrets` (`ichor create credentials`, `bundle-export`) stay out of the built-in roles by design. ichor-ui's ClusterRole gets `create` and `get` on the requests and the two `issue` verbs. Its namespaced Role keeps only `create` on Secrets (MachineReclaim credentials) and, with Ichor users, the named `ichor-user-credentials` rules. The installer's ClusterRole lists the new CRD.
- **Upgrade notes.** An install with `ichorUI.oidc.enabled` and empty `impersonate.groups` or `impersonate.users` no longer renders: list the groups and users, or set `ichorUI.oidc.impersonate.anyUser=true` for users. The controller image and the chart must be upgraded together (the backend needs the controller to answer its requests; a new backend with an old controller waits 20 seconds and fails each read).
- Not done: a UI choice of the `credentials-talos` lifetime shorter than a day (a rotation hand-off must outlive the rotation); the controller's and the CLI's own dial certificates keep a year (section 3).

### 2. Impersonation (F1, F7)

Decided: ichor-ui's ServiceAccount may impersonate only named groups and only named users, written by the chart or the controller; there is no "any name" mode unless the operator says so in a value.

- **Groups.** `resourceNames` is always emitted: `ichor:viewer`, `ichor:operator`, `ichor:admin` plus `ichorUI.oidc.impersonate.groups`. With OIDC on, the chart fails to render when `impersonate.groups` is empty (before, empty meant any group). A `system:` group can therefore never be impersonated, structurally.
- **Users.** Kubernetes cannot match a name by prefix, and a user such as `system:kube-controller-manager` is as dangerous as a group. With Ichor users (ADR 0094) the controller keeps the list: it maintains the ClusterRole `ichor-ui-impersonate` with one `resourceNames` entry `ichor:<name>` per IchorUser for users and one `ichor:<role>` per role any of them has for groups (custom roles are allowed, so the three built-in groups alone would not do). An empty list of rules grants nothing; a rule is never written without `resourceNames`. It reconciles on every IchorUser change and every two minutes, and does not watch ClusterRoles (that would need list and watch on all of them). It holds `escalate` and `update` on that one ClusterRole by `resourceNames`, nothing more, so it can grant an impersonation right it does not hold. The binding is installed by the chart. With OIDC on, `ichorUI.oidc.impersonate.users` must be listed, or the operator sets `ichorUI.oidc.impersonate.anyUser: true` to accept the residual risk knowingly; an empty list without the flag fails rendering. A new Ichor user can sign in a few seconds after creation (the controller's reconcile).
- **Rejected.** A Kubernetes structured authorisation config with CEL: its CEL only filters which requests go to an authorisation webhook, it cannot deny by itself, and it needs a webhook service in the managed cluster. A ValidatingAdmissionPolicy cannot see the impersonator. Forwarding a minted token instead of impersonating would move the problem to the signing key ichor-ui already holds for the issuer.
- **Residual risk, stated.** With OIDC and `anyUser: true`, a compromised ichor-ui can act as any user by name (not as a `system:` group), including users bound to powerful roles. Without the flag (the default after this change) it can act only as the listed users, which are the users Ichor is already trusted to represent.
- **The role is found by the name the install path produces.** The controller looks the ClusterRole up as `ichor-ui-impersonate` (`controller.ImpersonationRoleName`), and both install paths create it under that name: the install manifest defines it as `ui-impersonate`, which kustomize's `namePrefix` turns into `ichor-ui-impersonate`, and the chart names it `ichor-ui-impersonate` directly. The controller's own `get`, `update` and `escalate` rule and the installer's `bind` and `escalate` list name that one role. A missing role is reported as the condition `ImpersonationRoleReady=False` (reason `RoleMissing`, naming the role) on the `IchorInstallation` and a Warning Event, besides the log line, because nobody can sign in without it. An install made before the rename keeps an orphan `ichor-ichor-ui-impersonate` ClusterRole and binding with no rules, which are harmless and can be deleted.

### 3. Lifetimes (S4)

Decided: in-process dial certificates live 10 minutes (ichor-ui; minted per call by the controller on request, section 1). The controller's own dial certificate and the CLI's stay as they are: those processes hold the CA key anyway, so a shorter certificate gains nothing. Files handed to operators keep the default of one year (the user's decision: downloads are Ichor-side and a shorter default would break existing workflows) and gain a choice: `--ttl` on `ichor create credentials` (default and cap 8760h) with `--read-only` for an `os:reader` talosconfig, and the same two choices on the UI credentials download (1 year, 30 days or 1 day; read-only). `ichor create credentials` does not go through ichor-ui and creates no `TalosCredentialRequest`: it reads the secrets bundle with the caller's own Kubernetes rights and signs locally.

### 4. etcd backup key (S2)

Decided: backups are sealed with a key derived (HKDF-SHA256, info `ichor.maesh.dev/etcd-backup/v2`, salt cluster ID) from the secretbox encryption secret of the bundle, which only control-plane machine configs carry and which Ichor never rotates (so a CA rotation keeps old backups readable, ADR 0063). The v1 key (from `Cluster.Secret`, present in every worker config) is derived too and tried second when reading, so existing backups restore; every new backup is v2. Rotating the secretbox key is therefore not part of the CA rotation (section 6). Built: `etcdbackup.DeriveKey`, `Key{Current, Legacy}`, `Decrypt` tries both.

### 5. Maintenance pin (S3)

Decided: the first apply goes through an unauthenticated TLS connection, so Ichor pins what it can. The SPKI fingerprint of the maintenance certificate seen when the machine is discovered (re-recorded while the machine is not approved) is stored in the new `status.maintenanceFingerprint`, and the controller refuses to send the initial configuration, which carries the CA keys, to a node that presents another one. A machine that never went through discovery (added by IP, reclaimed) is pinned at its first provisioning probe. Within one `ichor init` run the identity read and the apply share one pin. Talos issues a new maintenance certificate when a node reboots or changes address; an operator who has checked the new fingerprint (named in the machine's Ready condition) accepts it with the annotation `ichor.maesh.dev/trust-maintenance-fingerprint`. This narrows the window to the time between discovery and apply; it cannot authenticate the first sight, so the provisioning network still must be separate (design, Trust). Built: `internal/controller/maintenancepin.go`.

### 6. CA rotation coverage (S6)

Decided: documented as a follow-up. Ichor's rotation covers the Talos API CA and the Kubernetes API CA. The etcd CA, the aggregator CA, the service-account signing key and the secretbox key are not rotated. Kubernetes needs a dual-key period for the last two (the old key must keep verifying or decrypting until every token and Secret is re-written), which is a multi-stage operation with a re-encryption pass, not an extension of the current two-CA stages; the etcd CA rotation needs every member restarted with both CAs trusted in a defined order; and the backup key (section 4) derives from the secretbox secret, which would have to be versioned first. The limit is stated in the docs so that "rotate after compromise" is not read as complete.

## Secrets handling

- **Restore marker (S7).** The marker in the backup bucket is stored as `{"marker": ..., "mac": ...}`. The MAC is
  HMAC-SHA256 over the marker JSON, keyed by HKDF over the backup passphrase with info
  `ichor.maesh.dev/etcd-backup/marker/v1`, so it follows whatever key material the backup passphrase derives from.
  A signature mismatch is an error. Snapshot rollback by replaying an older valid snapshot is not addressed here.
  Amendment (before v0.1.0): an unsigned marker is refused as well (`ErrMarkerSignature`, "take a new backup with this
  version"); the earlier compatibility path for unsigned markers served builds that never shipped, so it was removed.
- **Scrubber (S8).** `bundleSecretMaterial` is derived by reflection over every exported string and `[]byte` field of
  the Talos secrets bundle (trimmed, so a PEM that lost its trailing newline still matches), so keys the bundle gains
  or that were missing (etcd, aggregator and service-account keys, encryption secrets) are redacted. Rotation CAs were
  already added by the rotation code. Base64 re-encodings are not scrubbed.
- **Local files (S9).** `saveKubeconfigFile` now chmods an existing directory to 0700 like `saveBundleFile`. The local
  `secrets.yaml` stays plaintext (0600, atomic); encrypting it is deferred, but `loadBundleFile` now warns on stderr when
  the file is group or world accessible. Downloaded etcd snapshots were already written 0600; the CLI now states that
  they are not encrypted.
- **Reclaim Secret name (S10).** Uses `crypto/rand` (`rand.Text`, lowercased, 16 characters) instead of the
  `math/rand` based `utilrand`.
- **Other (S11).** The manager logs in production mode (JSON, no stack traces on warn); `--zap-devel` turns development
  mode back on, other zap flags are unchanged. The kubetrust trust file is written through a unique `os.CreateTemp`
  file in the same directory and renamed (mode 0644, public CAs only). Refusing `http://` S3 endpoints is left to the
  endpoint gating work.

## Typed hardening options for managed clusters

Decided: every hardening of a cluster Ichor creates is a typed field of `TalosCluster.spec.security`, off by default, for new and existing clusters. Unset means the rendered machine config and Cilium values are byte-identical to before. Machine config stays typed: Ichor builds the Talos documents itself, below every patch, and no raw YAML is accepted. `docs/guides/hardening.md` lists every option, what it does and what applying it costs.

- **Firewall** (`security.firewall`). Enabled renders `NetworkDefaultActionConfig` `block` and one `NetworkRuleConfig` per service (`ichor-fw-*`) following the Talos v1.14 recommended control-plane and worker rule sets: apid from the controller, operators and control planes; trustd between nodes; kubelet from control planes and the pod subnets; etcd between control planes; 6443 from the controller, configured sources, nodes and the pod and service subnets; Cilium tunnel (8472, or 6081 for geneve), health (4240) and WireGuard (51871); KubeSpan (51820). `allow` entries open host ports for host-network services. The field set needs the node CIDRs as input because render sees one machine at a time. The preflight is the admission webhook: it refuses a firewall whose `controllerCIDRs` does not contain the address the webhook's pod routes to the endpoint from (a UDP connect, nothing is sent; skipped when the endpoint does not resolve). No reboot (fieldmeta already classes both kinds reboot-free). Cilium masquerades pod traffic to another node's address, so the controller reaches apid on its own node from its pod IP and on any other node from its node's IP; `controllerCIDRs` must therefore list both the pod range (or the node's pod CIDR) and the node address, as the guide says. For the same reason a pod on node A that talks to a host port on node B is seen as node A: pod-level restrictions hold only for the host ports of the pod's own node, and any pod on a listed node reaches what that node's address may reach. A `controllerCIDRs` narrowed to one node's pod CIDR locks the controller out when it is scheduled on another node. The webhook also refuses a firewall change whose `controlPlaneCIDRs` miss an approved control plane's address (the controller reaches the other nodes from it, so Ichor itself would be cut off; the address is the machine's observed or declared endpoint, hostnames are skipped). A `nodeCIDRs` that misses a machine and an empty `talosAPICIDRs` are warnings only: errors are for what breaks Ichor's own operation or cannot render, and advice about the user's cluster is a warning. A node the controller can no longer reach cannot be repaired by reverting the spec, because the controller cannot deliver it; the way back is to patch the machine configuration from a source in `talosAPICIDRs` with a `NetworkRuleConfig` that lets the control plane reach apid (50000/tcp), after which the controller recovers and removes the temporary rule once the spec is reverted. Keep a `talosAPICIDRs` entry for an operator workstation before enabling the firewall; without one the way back is the console or a reset. A port that no rule opens is dropped, not refused. Not done: applying in Talos `try` mode with automatic revert.
- **WireGuard** (`security.wireGuard`). Sets `encryption.enabled`, `encryption.type: wireguard` and `encryption.nodeEncryption` in the effective Cilium values, after the user layer, so the typed option wins. Enabling WireGuard rolls the Cilium DaemonSet: the managed Cilium values carry `rollOutCiliumPods: true` whenever `wireGuard.enabled` is set, so the chart puts a `cilium-config` checksum on the agent pod template and the DaemonSet rolls (rolling update) when the Helm Job changes the config; without the switch the agents keep running with encryption disabled while the config says otherwise. The existing values hash re-runs the Helm Job; no node reboot. `CNIValuesApplied` is set only after the DaemonSet has rolled out (observed generation, updated and ready pods), so it means the agents run the new values. The switch was chosen over a controller-side annotation patch because Helm owns the DaemonSet and the chart already has it. Strict mode is left to `spec.cni.cilium.values`.
- **Pod Security and audit** (`security.podSecurity`, `security.audit`). Merged over Talos's own `KubeAdmissionControlConfig` PodSecurity document, so only the levels set change and `kube-system` stays exempt; audit is one of three presets (`metadata`, `rbacChanges`, `writes`), none logging Secrets or tokens above Metadata. Both need a v1.14 contract and are refused on an older one rather than silently raising it. The kube-apiserver restarts (fieldmeta `apiServerRestart`), no node reboot, and only when a config rollout is started: the control plane stays `Ready=False APIServerRestartRequired` until `ichor rollout config --cluster NAME` runs (ADR 0080's amendment leaves API-server restarts to a config rollout; the `APIServerRestartRequired` and `RebootRequired` messages and the guide name the command). During the rollout the API server is unreachable and kube-controller-manager and kube-scheduler restart once each (lost leases).
- **Disk encryption** (`security.diskEncryption`: `tpm`, `nodeID`, `kms`). Renders `VolumeConfig` for STATE and EPHEMERAL (LUKS2, slot 0, EPHEMERAL locked to STATE); `static` is not offered; `kms` must be `https`; `requireSecureBoot` maps to the TPM key's `checkSecurebootStatusOnEnroll`. On a cluster with approved machines the webhook refuses enabling or changing it unless the annotation `ichor.maesh.dev/confirm-disk-encryption-wipe: "true"` is present; Ichor never wipes a node, the guide documents the one-node-at-a-time reset-and-add path. Ichor records no TPM inventory, so it cannot pre-check TPM presence; Talos's own enrolment failure is the check: a node with `type: tpm` and no TPM installs, reboots and stays in stage `booting` with its STATE volume failed. Ichor reports the failed volumes and their error in the `Ready` message of a node stuck in `booting`. Talos's STATE volume locator names the system disk before Talos knows which disk that is, and recovers by itself, so only that exact locator message (`error evaluating disk locator: no such attribute(s): system_disk`) is left out of the NodeStarting message, and only for 3 minutes after the configuration was stored (`volumeSettleWindow`); it is shown when it outlasts the window (a node that never learns its system disk). Other failures are shown at once, because a real failure (a TPM-sealed volume on a machine without a TPM) arrives in the same stage with the same prefix.
- **Talos API access from pods.** A `TalosConfigPatch` with `machine.features.kubernetesTalosAPIAccess` is admitted with a warning (stronger wording for `os:admin` in `allowedRoles`), not refused, and the `override` verb is not consulted for this rule: Ichor itself is hardened strictly, while advice about the user's own cluster is a warning (the user's direction of 2026-11-02). Render drops the feature from non-control-plane machines (Talos allows it on control planes only), so a cluster-layer patch works and renders where it is valid. An update that leaves the documents alone is not re-checked. The rule lives in `internal/webhook/v1alpha1/security_options.go`.
- **Not modelled.** SecureBoot and UKI, kernel lockdown, an `os:reader` talosconfig role, kubelet serving-certificate bootstrap: follow-ups.

## Resetting, removing and re-adding a node

- **A removal whose drain fails** (a bare pod, for instance) returns the error, so the reconcile is retried with backoff; it writes the pod into the `Removal` condition and a Warning Event. There is no force-drain option: the guide says to delete the pod.
- **The typed confirmation.** A reset asked for by hostname is stored with the machine name as `confirm`, which the TalosOperation CRD compares with `machineRef.name`.
- **A cordon Ichor makes is Ichor's to lift.** The removal drain marks a cordon it makes with `ichor.maesh.dev/cordoned-by-ichor: removal`, and never when the Node was already cordoned, so a human's cordon is never claimed. The Node object is kept and re-used when the machine rejoins, so it would come back `SchedulingDisabled`: when a machine's Talos node is reachable and its Node is Ready and carries the reset annotation (`ichor.maesh.dev/reset-by-ichor`) or that marker, the controller uncordons it and drops both annotations. A Node in the middle of a rollout drain is left to the rollout.
- **The Kubernetes Node.** The reset code keeps the Node on purpose (a delete could race the kubelet registering it again, `nodeResetByIchorAnnotation`), and discovery ignores its address while it is not Ready. ADR 0135 later deletes the Node after the wipe.
- **Roll-out visibility.** The controller logs an Info line when it starts and finishes applying a rendered configuration without a reboot (machine, changed paths, config hash); reboot rollouts record Events.

## Ichor's own pods tolerate tainted control planes

`ichor init` with a preset whose control planes are tainted (`schedulable: "false"`: `standard`, `large`) must reach the Cilium hand-over before any worker exists. The Cilium chart gives the `hubble-generate-certs` Job (`certgen.tolerations`) no tolerations, so on tainted control planes it stays Pending, the agents wait for its secrets and the hand-over never completes before a worker is approved. Ichor therefore sets `certgen.tolerations` in the managed Cilium values to the control-plane `NoSchedule` taint. It is a default a user can still override in `spec.cni.cilium.values`; the values hash changes once on upgrade, which re-runs the Helm Job. `cilium-operator` already tolerates the control-plane taint, so it needs no change. `ichor-ui` (installer manifest and chart default `ichorUI.tolerations`) tolerates the control-plane taint like the controller. When the hand-over wait times out on a cluster with `schedulable: "false"`, `ichor init` says that a worker may need approving (`ichor approve node`). Ichor's own pods get more reach; nothing in the user's cluster is restricted.

## The controller still reaches the API server after an etcd restore

The tail of an etcd restore replaces the stale kube-proxy and Cilium pods through the Kubernetes API (`etcd_restore.go`, with the pod-restart Role). When the controller itself runs on a worker whose kube-proxy is stale, the Service address of the API server is refused (`connection refused`: kube-proxy rejecting a Service it thinks has no endpoints) and the controller cannot start the tail that would repair it. ADR 0089 records the same symptom. The Cilium egress policy is not believed to contribute: its `kube-apiserver` entity rule drops (a timeout) rather than refuses, an inference from the symptom. Two measures:

- The controller keeps the InternalIPs of the control-plane Nodes in `/var/run/ichor/trust/apiservers` (the emptyDir that survives a container restart). When the Service address has not answered for 30 s, its start-up wait tries those addresses too, alternating with the Service address (the certificate is verified as `kubernetes.default.svc`, which Talos puts in the apiserver certificate), and stays on the address that answered until its next start (`cmd/apifallback.go`).
- Both install paths prefer a control plane for the controller (`preferredDuringSchedulingIgnoredDuringExecution`; the chart's `manager.affinity` default).

Limits: a controller pod rescheduled as a new pod has a new emptyDir and no file, so the first measure helps a restarting container, not a fresh pod; the second applies only when the pod is next scheduled.

## RBAC: the Cilium Job keeps the hubble Role mirror; escalate by name is added for the other Cilium Roles

Helm's escalation check refuses to create a Role or ClusterRole that grants a rule its caller does not hold. ichor-cni holds the Secret rights of the chart's `hubble-generate-certs` Role, rule for rule (`hubble_role.yaml`, mirrored in the chart copy, ADR 0103, 1.2).

Relying on `bind` and `escalate` by `resourceNames` alone does not work: the escalation check does not honor `resourceNames` on `escalate` for a Role that is being created, and a `create` verb on Secrets cannot be name-scoped, so the Cilium 1.19.10 takeover fails with `roles.rbac.authorization.k8s.io "hubble-generate-certs" is forbidden: ... attempting to grant RBAC permissions not currently held: {APIGroups:[""], Resources:["secrets"], Verbs:["create"]}`. The mirror is required for the create.

What stays: `bind` and `escalate` on `clusterroles` and `roles` restricted by `resourceNames` to the names the embedded chart renders under Ichor's values, one rule per kind (ClusterRoles `cilium`, `cilium-operator`; Roles `cilium-config-agent`, `cilium-operator-ztunnel`, `cilium-operator-tlsinterception-secrets`, `cilium-tlsinterception-secrets`, `hubble-generate-certs`). The list is kept equal to the rendered chart in both directions. Whether these name grants are needed beside the mirror is open.

Open for the user (ADR 0108 decision): whether the Job may keep a Secret mirror for the create, or the chart's hubble Role should be created by a different identity, since a name-restricted escalation cannot replace it.

## RBAC: ichor-ui reads the trust ConfigMap by name

GetEffectiveConfig renders in ichor-ui, and with `spec.authentication.ichor.enabled` the render reads ConfigMap `ichor-oidc-trust` (ADR 0094). The ServiceAccount had no ConfigMap rule, so the node page's Effective config tab failed with `forbidden`. Nothing stored by the controller can stand in for it: the tab renders from the CRs and the bundle on every call, there is no stored render. Decided: `get` on `configmaps` with `resourceNames: ichor-oidc-trust`, in the namespaced Role in `ichor-system`, never list or watch. The rule lives in `internal/uiapi/rbac_markers.go`, and `config/rbac/ichor-ui/role.yaml` and the chart's `ichor-ui-secrets-role.yaml` carry it.

## Amendment 2026-11-04: the UI no longer signs out after its own password change

Token revocation (F6) is unchanged: a password change still moves `notBefore` and drops every refresh family. The line "The UI signs out after its own password change" is replaced by ADR 0094's amendment of the same date: the tab signs in again with the new password through the normal login, so only the user's other sessions end.

## Amendment 2026-11-05: rediscovery after a reset, and approving without a sign-in

- **Discovery looks again soon after `ichor node reset`.** The Node object is not the cause: a Node marked `reset-by-ichor` is already ignored by discovery once it is not Ready (see `knownHosts`). The causes are timing. The pass that follows the reset sees the Node still Ready (the kubelet is gone, but the node lifecycle controller waits about 40 s) and counts the address as a member; the wiped machine is back in maintenance mode about a minute after the reset; and nothing started a pass in between, so the next one was up to `discoveryRequeueInterval` (five minutes) away. The cluster reconciler now watches Nodes that carry the reset marker (it wakes when the marker is written and when the Node stops being Ready) and, for `discoveryFreshWindow` (3 minutes) after the time held in the marker, looks again every `discoveryFreshInterval` (15 s). The Node is still not deleted: the controller holds `get/list/patch/watch` on nodes and no `delete`, the kubelet of a node that is not yet down re-registers a deleted Node, and the uncordon-on-rejoin path relies on the Node being reused; granting `delete` on every Node of the cluster would buy nothing the 15 s pass does not.
- **`ichor approve node` without `--local` on an `--allow-unauthenticated` install** is refused with `you need the "approve" verb on talosmachines/approval`. That is the design above: with no sign-in the webhook asks the right as ichor-ui's ServiceAccount, whose role (`config/rbac/ichor-ui/role.yaml`, the `talosmachines` rule: delete, get, list, update) has no `talosmachines/approval`, and `checkApprover` (`internal/webhook/v1alpha1/talosmachine_webhook.go`) fails closed. Granting the verb to the ServiceAccount would let anyone who reaches an open ichor-ui hand the cluster's configuration, CA keys included, to any machine at a declared address, which is what the right exists to prevent. `ApproveMachine` returns `PermissionDenied` and appends: without a sign-in, run the command with `--local` (the user's own kubeconfig, which needs `ichor-operator` or `ichor-admin`) or turn on Ichor users or OIDC; with a sign-in, bind the user to a role that holds the verb.

Amendment (2026-11-05): three consequences of the 15 s rediscovery.

- **A plain `ichor node reset` must not trip over the machine discovery recreates.** The wait for the removal flow (`awaitRemoval`) looked the machine up by name. With the 15 s pass, discovery recreates a pending TalosMachine under the same name (the UUID) between the removal's last step and the operation's next reconcile, so the operation would find the new object, try to delete it, and the TalosMachine webhook would refuse (`delete refused: set the annotation ichor.maesh.dev/allow-delete="true"`). The operation records the UID of the machine it started on (`status.node.machineUID`, a new optional field) when the reset begins, and treats "gone, or replaced by an object with another UID" as the removal being complete; it deletes with a UID precondition, so a replaced object is never deleted. `RemoveMachine` in the UI API deletes the object it has just updated and carries the same UID precondition; `clearStalePending` in the CLI deletes pending machines on purpose, listing them first. An operation recorded before the field existed has no UID and keeps following the name.
- **The NodeStarting message of a fresh install does not report the locator message.** See "Disk encryption" under "Typed hardening options": only the exact STATE locator message is left out, and only for 3 minutes (`volumeSettleWindow`).
- **A stale `AdoptionHeld=True` condition does not outlive `hold-apply`.** Only the running-node path (`reportHold`) removed it, and a node in maintenance mode never reaches it. The reconcile now drops the condition as soon as it sees the annotation gone, before any path runs; the status write of that path persists it.

Amendment 2026-11-05 (ADR 0129): the role-grant guard of `UserService` now also runs in a validating webhook on `ichorusers`, so a user who may `update` `ichorusers` cannot grant roles they do not hold with `kubectl` either.

## Amendment 2026-11-05: a spoofed maintenance node cannot take over an approved machine

The maintenance-certificate pin of section 3 is dropped for a converged machine (ADR 0076, amendment of 2026-11-05), and discovery could write a twin's address into `status.observedEndpoint` of an approved machine, so a node that merely claimed an approved machine's UUID, serial and MACs could receive its configuration. `Discover` now follows a discovery match only for unapproved machines and for approved ones that are not yet configured and have a pinned certificate; the cluster lock's stopped-holder rule no longer treats a re-provisioning control plane as finished. See the amendments to [ADR 0076](0076-approved-machines-are-provisioned-through-the-maintenance-api.md) and [ADR 0086](0086-a-moved-node-is-followed-through-status-not-spec.md).

Amendment 2026-11-06: the controller Deployment's resources and probes. On a 3 control plane + 1 worker cluster a 256Mi memory limit OOMKilled the controller, and a liveness probe timing out at the default `timeoutSeconds: 1` and a lost leader election restarted it as well; while it is down the admission webhook (`failurePolicy: Fail`) refuses every Ichor write. The controller Deployment (`config/manager`, the chart's `manager/manager.yaml` and `values.yaml`, kept in step) therefore has a memory limit of 512Mi (request 256Mi); a CPU limit of 1 (request 100m, up from 10m so the pod is not starved first); `GOMEMLIMIT=400MiB`, a soft Go heap limit below the container limit, without which the GC lets the heap grow towards the kernel limit (keep it at about 80% of `resources.limits.memory` if that is changed); and liveness and readiness `timeoutSeconds: 5` with liveness `failureThreshold: 3` (the handlers are `healthz.Ping`, no work: a timeout means a starved pod, and three 20 s periods ride it out). ichor-ui's probes get `timeoutSeconds: 5` as well (its 384Mi limit already covers two argon2id hashes; the same CPU limit applies). What uses the memory: the in-process Cilium values validation allocates about 14 MB per call and the chart render 36 MB (the controller never renders for Jobs: Helm runs in the Job's pod), and the machine-config render for the validation facts adds more. The cached informers are scoped to the controller namespace where the Role says so (`CacheOptions`) and drop `managedFields` from every cached object (`cache.TransformStripManagedFields`, a large part of a Node's or Job's metadata). No cluster-wide cache of Secrets, ConfigMaps or Services exists, and the Pod, DaemonSet and Deployment reads go through the uncached `APIReader`. The embedded chart is parsed once for validation (`loadChart`, `sync.OnceValues`); `renderChart` parses it afresh per call because Helm mutates it, and only the CLI, the Job and the validation of non-empty user values call it. The heap of a loaded controller has not been profiled, and pprof is not exposed.

## Amendment 2026-11-15: sign-in is the `ichor init` default

The line above that says making users the `ichor init` default "was left out of scope" is superseded: `ichor init` turns Ichor's own sign-in on by default, with the issuer `https://localhost:8443` unless `--ui-url` gives another, and `--allow-unauthenticated` restores the open mode explicitly. Its warning now says that anyone who can reach ichor-ui can change the cluster with ichor-ui's permissions, including resetting nodes. `--ui-url` no longer turns anything on; it only sets the issuer. The issuer is changed afterwards on the TalosCluster's `spec.authentication.ichor.url` (ADR 0094's amendment of the same date). `ichor adopt` still starts ichor-ui open; see that amendment for why.
