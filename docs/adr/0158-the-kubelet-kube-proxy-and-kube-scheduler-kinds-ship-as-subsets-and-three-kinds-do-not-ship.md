# 0158. The kubelet, kube-proxy and kube-scheduler kinds ship as subsets, and three kinds do not ship

Status: Accepted · Date: 2026-11-13 · Design section: Typed configuration · Amends: 0155, 0157

Decided: `KubeletConfig`, `KubeProxyConfig` and `KubeSchedulerConfig` are added to the union (fields `kubeletConfig`, `kubeProxyConfig`, `kubeSchedulerConfig`). Each carries its `config` payload as a local subset of the upstream Kubernetes configuration type: the fields an operator is documented to set on a Talos node, with every field left out named in a table and refused when a Talos document sets it. `KubeAuthenticationConfig` is reclassified as Ichor-owned, `KubeAdmissionControlConfig` as unstructured, and `KubeStaticPodConfig` is in the union with its pod carried whole as the core v1 `PodSpec`, its CRDs applied with server-side apply. Of 65 accepted kinds, all 65 are in the union.

## Context

ADR 0155 held back nine kinds whose payload is a free-form field, ADR 0157 shipped three of them, and six remained. The upstream types of the kubelet, kube-proxy and kube-scheduler configuration cannot be written as a CRD schema whole: they contain floating point numbers, a quantity type with no schema, a duration type with an untagged field, and (in the scheduler) a list with no list type. The scheduler type is also large. A kind that accepted such a document and dropped its payload would be worse than no kind, because the author would believe the setting applied.

## Decisions

1. **The subset is what an operator sets, not what a schema tool can express.** Picking by what a tool can express would choose the shape by a tooling limit and could leave out the one field anyone wanted. A field is carried when Talos's or the component's own documentation has an operator set it on a Talos node, and the generator carries every field of the upstream type that no row of the omit table names. The table (`omits` on the field override) is where each omission is recorded, with one of four reasons: Talos refuses the field in a kubelet configuration, the field's type has no CRD schema, its value is free-form, or it is not among the fields an operator is documented to set.
2. **What each carries.** The kubelet subset carries the fields behind serving certificates, graceful shutdown, swap, eviction, reserved resources, CPU, memory and topology management, pod limits, feature gates, unsafe sysctls, container log rotation, image garbage collection, taints at registration, the cluster domain, image pull settings, user namespaces and tracing. The kube-proxy subset carries the bind and metrics addresses, node port addresses, the cluster CIDR, local traffic detection, the iptables, IPVS, nftables and conntrack blocks, feature gates and the OOM score adjustment. The scheduler subset carries `profiles` with their `plugins`, and `percentageOfNodesToScore`.
3. **Not carried, on purpose.** The kubelet fields Talos protects (`authentication`, `authorization`, `cgroupRoot`, `kubeletCgroups`, `systemCgroups`, `port`, `protectKernelDefaults`, `resolvConf`, `rotateCertificates`, `staticPodPath`, `seccompDefault`): a field Talos refuses is worse than a field left out, and a CRD field cannot be withdrawn. The floating point and quantity fields: `memoryThrottlingFactor` and `logging` of the kubelet, `clientConnection` and `logging` of kube-proxy, `leaderElection` and `clientConnection` of the scheduler, and the scheduler's `extenders`. The scheduler's `profiles[].pluginConfig`, whose arguments are a free-form object: scoring strategy tuning and any other plugin argument is therefore not expressible. Every other omitted field is in the table with its reason.
4. **Typed fields Ichor owns.** The `image` of each of the three documents follows `spec.kubernetesVersion` and is set by the Kubernetes upgrade. `enabled` of kube-proxy belongs to `spec.cni.kubeProxy`. `enabled` of kube-scheduler is part of the control plane's shape, which Ichor owns, and a config patch may not switch it off. Neither is in the CRD, and a Talos document that sets one is refused with the field and the owner named.
5. **An omitted field is refused, not trimmed.** Reading a Talos document into the typed form fails on any field the subset does not carry, naming it, at any depth. In the cluster, the API server removes a field its schema does not have from the stored object unless the client asks for strict field validation, which `kubectl` does by default: such a client is refused with the path of the field. A client that does not is not told. That gap belongs to the API server, not to the webhook, which only sees the object after the field has gone.
6. **Fields keep their upstream type, with two exceptions.** A field whose upstream type is a struct value becomes a pointer, so that an unset duration or block is left out of the rendered document instead of written as a zero value. List type and map key markers are not copied: the scheduler's profiles are keyed by a name with no default, which a CRD refuses, so lists are atomic. Schema markers that validate a value are copied.
7. **Fields are added by deleting an omit row.** The set is append-only like every CRD field: a field carried cannot be taken back, so a doubtful field stays omitted until someone needs it.
8. **`KubeAuthenticationConfig` is Ichor-owned.** Ichor renders this document itself (ADR 0094), and Talos merges it by replacing its `configuration`. A patch carrying it would replace Ichor's issuers and drop the cluster's own sign-in. Its classification said a patch was merged over a baseline, which is not true of a replacing field.
9. **`KubeAdmissionControlConfig` is unstructured.** Its payload is one free-form configuration per admission plugin, so no single schema exists, and Ichor already writes the Pod Security plugin itself. What a patch cannot express there (Pod Security exemptions and versions other than the latest) belongs on `spec.security.podSecurity`.
10. **`KubeStaticPodConfig` ships, and its CRDs are applied with server-side apply.** A static pod needs a security context, host networking, host path volumes and capabilities, so its pod is carried whole as the core v1 `PodSpec`, not as a subset. The schema is about 300 KB of compact JSON in each of the two CRDs that embed the union. Client-side apply, as `kubectl apply` does without `--server-side`, writes the whole object into the `kubectl.kubernetes.io/last-applied-configuration` annotation, which the API server limits to 262,144 bytes, so it refuses these CRDs. Server-side apply writes no such annotation. `make install` and `make deploy` therefore pass `--server-side`, and the installer and `ichor init` already apply server-side. The chart is installed by Helm, which applies server-side by default in Helm 4, the version `install-helm` fetches. A patch whose pod is large can still exceed the limit when a person applies it client-side, since it is the object itself that is annotated; an ordinary static pod is far smaller. The accepted count and the shipped count are both 65.
11. **Two Kubernetes configuration modules become direct dependencies**, `k8s.io/kube-proxy` and `k8s.io/kube-scheduler`, alongside `k8s.io/kubelet`, at the Kubernetes version Ichor already builds against. Only their types are used, to name the fields of the subsets.

## Rejected

- Mirroring the whole upstream type: five of the six cannot be written as a schema, and the sixth is too large.
- A raw object for the fields a schema cannot express: it is the free-form escape hatch the typed-only rule forbids.
- Dropping an omitted field quietly, as the secret fields are: an operator would see a kind that appears to support a setting that does nothing.
- Shipping a field Talos itself refuses.

## Consequences

An operator who needs a setting outside a subset cannot set it through these kinds until its omit row is deleted and a release carries it; the omit tables are the list. Plugin arguments of the scheduler stay unreachable. `TalosCluster` embeds the union, so each subset is paid twice in CRD size; the scheduler's `plugins` block is the largest part of that.
